# Deployment

Pi Stack separates reviewed source from host-owned accounts, credentials, network routes and release paths. This guide describes the shared deployment contract. A host handbook owns its actual values and acceptance receipts.

## Native history migration

Publication observes the [native history boundary](native-history-boundary.md) before selecting new artifacts. Old owners continue accepting new agents, messages, questions and scheduled wakes while their work runs. A naturally idle owner uses a short dispatch-only replacement; normal receipt identities survive transient listener replacement. Each owner migrates inside its retained private namespace after its old writers close. Locked owners use the same preserving first-unlock transform. Preserve the [migration](native-history-migration.md)'s private snapshots/preimages in backup coverage. New databases use native history directly.

## Host platforms

The maintained publication owner runs on an Ubuntu 26.04 local server and releases the same integration to that server and a Debian 12 remote VM. External Meet transcription uses the CPU-only [Meet recognition service](../apps/meet-recognition/README.md), declared by each host.

Ubuntu and Debian provision packages and systemd units through their host handbooks. NixOS remains a supported host arrangement: declare equivalent packages, units and access gates in its configuration, then activate its generation through that host's handbook. NixOS activation commands do not apply to Ubuntu. Public source does not own machine names, SSH aliases or filled-in target configuration. Preserve publication target IDs across host replacements while receipts still carry custody.

## Publication owner

From a writer checkout, submit an immutable commit:

```sh
deploy/publication submit "$(git rev-parse HEAD)"
```

Before it pushes the immutable request ref, `submit` fetches current `main` and refuses a source commit with any Git root absent from that branch. Merging current `main` into a checkout with another root does not make it safe: replay the intended changes onto current `main` instead. A shallow checkout or grafted history cannot prove this ancestry and is rejected. The gate protects the request ref as well as the later integration push. Submission also requires ancestry of the installed owner's retained `refs/pi-stack-publication/owner-source` before pushing the immutable ref or accepting queue custody; an omitted bootstrapped repair is a source-admission error, not a late deployment attempt.

The receipt acknowledges durable custody of the submitted exact SHA. `sourceSelection.status: pinned` records that SHA as the deployment candidate, with an immutable `deliverySource` ref. Updating `main` is best-effort fast-forward publication of source history: it does not hold deployment, replace the candidate, restart its qualification or invalidate an in-flight delivery. The owner retains immutable source, commands, artifacts and per-host outcomes through restarts. A resumed coordinator reselects the retained integration in its shared checkout before consuming cached artifacts or adopting publication code; another request's checkout selection never replaces the pinned candidate. Selection failure retains the command and diagnostics without invalidating proofs or repeating completed host delivery.

Each configured host has an independent durable delivery lane:

- **kenan-server:** build required artifacts and deploy, with service-start recovery only. Its delivery path runs zero tests, doctors, qualification, warm-up or browser gates.
- **Converge:** independently prepare changed-source builds, start services and establish source health under `minimal` mode. Its wait, failure or repair cannot delay or roll back kenan-server.

Tests, proofs and doctors outside the minimal Converge lane run after serving and retain truthful outcomes, separately from delivery. `checks.status: deferred` remains explicit until post-serving evidence exists. Once each host lane passes, `pi-stack-publication-post@REQUEST--SHA--HOST.service` runs full checks, Android tests and host proof for that host, without waiting for another host. Its durable receipt is `STATE/post-serving/REQUEST/SHA/HOST.json`. Failed diagnostics alert their owner; they never change serving state or roll back a host. There is no fleet-wide success gate. Reports name which host serves the candidate, which remains pending or failed, and which checks passed, failed or were not run.

Each host retains source-history, native-history and accepted-job custody before changing serving state. Private namespaces, credentials and access grants remain host-owned; source publication does not activate the off-by-default Root Kenan transaction or change a person's execution identity. It installs matching Android/web artifacts before server activation; artifact hashes establish byte integrity. Immutable components prepare while existing controllers serve; only source-changed owners replace their processes. Remote builds once and Kenan copies that web output. A completed host releases its reservation immediately. Another host's meeting, native prerequisite, executor handoff, lock or failure neither delays nor replays that delivery.

`deploy/publication inspect REQUEST` shows progress. Submitting the same source SHA returns its receipt or rejects an unrepaired failure. `deploy/publication cancel REQUEST` records cancellation at the next command boundary; it does not terminate accepted work or undo a completed host release.

After creating `/etc/pi-stack/publication.json`, install committed owner source with `deploy/publication install --bootstrap`. It takes the worker lock nonblockingly, retains the source at `refs/pi-stack-publication/owner-source`, installs the command/modules and publication systemd units, reloads the user manager and enables the wake path and timers. A busy worker refuses bootstrap. `deploy/publication install --code-only` takes the same lock and retains source, but updates only code without changing units or waking work. Both require an initialized publication repository and committed source.

Publication adopts the submitted candidate's own `deploy/publication install` under the existing worker lock. The candidate owns its module inventory and installation recipe. Admission and owner adoption require ancestry of the retained owner source; a later release cannot erase an installed repair. Merge a missing retained source ref into authorized publication source rather than weakening this check. Cancellation remains binding.

[`config/publication.example.json`](../config/publication.example.json) shows the schema. Set:

- `repositoryUrl` to the canonical Git origin and `mergeAuthor` to the name and email for integration commits.
- `targets` in attempt order, not as an all-host readiness barrier. Each has a stable receipt `id`, an expected supervisor `environmentId`, an SSH alias or `null` for the sole local target, absolute `releaseCommand`, `releaseRepository` and `checkServicesCommand` paths, a `hostConfig` path, `requiredUnits`, and a loopback `voiceStatusUrl`. Remote targets also specify an absolute writable `androidTransferRoot`.
- `paths` for the publication user's canonical checkout, ignored Android `local.properties`, state directory, installed command, user unit directory, repair workspaces, Pi CLI and alert inbox. Omitted paths use home-relative defaults, except for the alert inbox.

The file contains host identities and routes, not credential values. `PI_STACK_PUBLICATION_CONFIG` selects a different file for a fixture. Provision it before either installation or submission. Keep target IDs stable while receipts carry maintenance or restoration custody. The target's host file supplies `fleetUser`. Its installed `checkServicesCommand` checks the router, failed runtime units, fleet service and every unlocked supervisor's unit. Runtime failures cover all Orchestrator and Remote instances (including locked people), router, Voice, Meet recognition and model brokers. Other failed `pi-*` units are reported on stderr and retained as `otherFailedPiUnits` in the final host proof, not treated as release dependencies. The host's `requiredUnits` adds any host-specific dependencies. A scheduled Claude balance collector failure caused an otherwise healthy release to be rejected on September 29; maintenance failure must remain visible to its host owner without vetoing an application release. Converge's independent health result checks each unlocked supervisor's health, commit and environment ID, along with the configured required units and Voice status. kenan-server uses service-start recovery rather than this qualification gate. Neither lane assumes any named person is unlocked. The remote SSH user must already have release authority. Its credential and Android signing key remain in host custody.

The worker's state is under `paths.stateRoot`, by default `~/.local/state/pi-stack-publication`. Requests are `queued`, `running`, `failed` or `published`. A busy first-activation gate returns to `queued` with `blockedSince`, `waiting.reason` and `nextAttemptAt`. Cancellation is a failed request with reason `cancelled`. Requests and repair receipts are the issue source of truth. `deploy/publication issues` reads their complete index without taking the worker lock, so inspection remains available during a release. The owner maintains one bounded alert at the configured inbox; `acknowledge-issues` silences the current notification without clearing repair or host custody. Each request retains durable successful host outcomes while waiting elsewhere. Delivery and check outcomes are separate: a remote failure leaves local serving intact and visible. Issue resolution names complete publication ancestry, receipts and actual host outcomes even after a source-root cutover. Retain those Git objects in the publication repository. A pending or failed host remains explicit; unrelated source and outstanding host restoration remain issues.

Chat reports and Machine alerts derive their current outcome from the same repair/ancestry resolution view. Routine repair progress does not replay a failure. Reports distinguish each host's serving result from post-serving check outcomes; a pending Converge lane does not conceal successful local delivery. Repair continuation retains the original requester and causal failure history.

To report back to a Remote thread, set `PI_STACK_PUBLICATION_REPORT_URL` and `PI_STACK_PUBLICATION_REPORT_SESSION` when submitting. `deploy/publication report REQUEST REMOTE_URL SESSION_ID` attaches a requester to an earlier request; without arguments, it reconciles an existing report only. `report.status: accepted` means Remote queued the report. `delivered` means its thread confirmed dispatch. Notices retry transport separately from release work. Submission validates the requester identity without probing its availability: an offline or retired requester cannot prevent custody transfer, including a repair successor. Notification failure remains in the report receipt; it is not deployment failure.

### Ancestry and live handoff

Source and artifact identity belong to the immutable request; readiness, ancestry, reservation and handoff belong to each host delivery. Before changing that host's intake or selecting source, the owner reserves it and checks that the submitted candidate descends from its selected live commit and release-checkout HEAD. Missing selected source is fetched by exact SHA from its configured `releaseRepository` and retained under `refs/pi-stack-publication/selected/<sha>`. The ancestry proof names the host and baseline; each wrapper repeats the check under its deployment lock. A divergent candidate requires an explicit source repair retaining the missing history, not disabled rollback protection or silent substitution of later `main`.

Newer requests may advance independently free hosts. An older request never downgrades a successful newer delivery or treats a moving branch as authority to change its candidate. Its receipts retain the exact source it delivered and any subsequent ancestry-based resolution, without relabeling a descendant as the submitted SHA.

`unified-threads-v1` has a per-host first-activation gate. For the host being activated, the worker records its fleet launch state, pauses new launches, waits for active runners and fleet work, then freezes its router, supervisors and pre-contract owner for a final census. Busy hosts are restored and retried without replaying accepted work. The recorded operator pause remains paused. An empty census permits the release wrapper to transfer native transcript references, held messages and pending results. Later releases use live controller handoff without the first-activation pause. A target that already selected the thread contract cannot be replaced by code without it.

Failure or cancellation restores recorded intake and service states for unfinished host work; it does not undo a proved successful delivery. Unrestored native-history custody is a per-host admission lease even when its transient deployment reservation was released. Before reserving a target, publication reads every other request's native-history receipt; any state other than positively `restored` or `released` produces a `native-history-custody` wait naming the original request and receipt. Failed or cancelled request status does not release that lease. Successors and unrelated admitted requests cannot reserve, census, advance native fences, install artifacts or activate on that host. Their wait probes read publication custody only. Clearing one host permits that host alone to proceed; the original owner retains its other hosts until their restoration or serving-native release is acknowledged. Checks/builds and independently free hosts continue normally.

Marked exit-75 outcomes are recognized across the complete command log segment, including interleaved output. The frozen boundary's exact `already preserved/migrated` restoration refusal produces `resume-required`: that host keeps its original integration custody, excludes competing publications and stops automatic restoration attempts. An evidenced infrastructure repair may resume that same integration after custody reconciliation. It cannot substitute a new application integration after forward-only migration. Unknown refusals remain errors; `repair-required` needs explicit recovery. A code-only owner repair may correct control handling without changing the pinned application candidate.

Each host reservation spans only that host's ancestry census, artifact installation, activation and serving outcome. The owner releases it immediately after durable delivery, or after restoring custody on deferral or failure. Interruption recovery is likewise per host. Unfinished restoration prevents another deployment to that host until repaired, without blocking free peers. The exact candidate and immutable artifacts remain reusable for unfinished targets. The owner never force-pushes, substitutes a merge for the submitted candidate or downgrades a successful host because `main` moved. Per-target delivery outcomes, check results, Android hashes and source refs stay with the request across waits, failures and retries.

## Publication progress and repair

[`deploy/publication-control.mjs`](../deploy/publication-control.mjs) owns command deadlines and retry budgets. A failed host receives bounded automatic retry under its existing source and restoration custody, plus an alert naming the host, SHA and causal failure. Exhausted retry remains an explicit failed-host outcome with repair custody; successful peers are never replayed or rolled back. Commands record arguments, cwd, start/deadline and log before launch. The watchdog inspects source work and each host lane independently; a stalled command's owning unit is stopped and its exact progress retained. Queue-claim supervision rechecks the receipt under the worker lock before acting. A probe, another queue head or a supervision gap resets that claim clock.

[`deploy/publication-hosts.mjs`](../deploy/publication-hosts.mjs) owns fsynced journals under `STATE/host-lanes/REQUEST/INTEGRATION/HOST/journal.json`. Each host runs in `pi-stack-publication-host@REQUEST--INTEGRATION--HOST.service` under that host's `flock`. Its immutable input selects both owner-code SHA and candidate SHA; a new owner installation cannot alter in-flight delivery code. Source coordination acknowledges systemd custody and continues without waiting for a host. Journal transitions use version 1 with `requestId`, `integrationSha`, `hostId`, `token`, `inputPath`, monotone `revision`, `state`, `fields` and `history`; live progress includes `step`, `progress`, `worker` and `timings`. States are `queued`, `running`, `recovering`, `passed`, `waiting` or `failed`; settled states carry a matching `outcome.status`. `fields` retain that host's delivery, reservation, executor-handoff, native-history, first-upgrade, maintenance and Android custody. The coordinator merges these journals without overwriting another host's fields. Revision/token conflicts are errors, not permission to replay effects.

Meetings, live telephone calls, native prerequisites/history and a busy executor handoff are explicit per-host external waits. Accepted jobs keep their execution identity and continue; publication neither cancels nor replays them. Accepting controllers keep serving; submitted source and built artifacts remain reusable. `executor-handoff` preserves the changed executor's pending replacement instead of failing a delivered Remote or cancelling active work. Bounded readiness probes resume only unfinished delivery; legitimate busy dependencies have no wait deadline and consume no deployment attempts. Other ready hosts and newer admitted requests proceed independently. Telephone probes use canonical serving configuration through `deploy/phone-census`, never install configuration or end calls. Unknown/unavailable census is an error, not an empty host. Consecutive meeting/telephone census errors have the configured two-hour failure window; native-source/history errors fail the affected host immediately. A failed native-history probe preserves `repair-required` custody, not automatic schema rollback.

`deploy/publication recover-native-history REQUEST HOST` explicitly reconciles the target's frozen restoration helper under its owning locks. Recognized restoration records `restored`; refusal/error retains custody and causal evidence. Cancellation, actual command failures and interrupted recovery remain explicit. Successful host outcomes are conserved; pending or failed targets remain visible without invalidating serving peers.

An explicit `STATE/always-open-source-hold.json` suspends worker draining and automatic retry/wake, not source intake or dedicated repair custody. Its version-1 contract requires nonempty `reason`, owning `threadId` and `releaseWhen`, with `applicationStop:false`. The watchdog exposes the hold in `worker-watch.json`, discards queue claim clocks while held and starts a fresh clock after the owner releases it. A malformed hold rejects execution. Running-command deadlines remain supervised; explicit restoration remains available. Only the hold's owner removes it after its release condition is satisfied.

A restored old-owner maintenance receipt is not reused as a new attempt. The successor's source-bound helper validates the previous acknowledged identity, absence of thread closure/admission fences and native readiness, and the exact owner ledger. An already prepared fleet barrier must belong to this new candidate; foreign custody refuses acquisition. It then creates a source-bound observation receipt, retaining the prior restoration receipt as evidence. Observation keeps ordinary intake and scheduled wakes open. Same-attempt recovery does not rewrite receipts or reacquire a restored attempt. Health checks execute before and after fence transactions, never while holding a live consumer's SQLite write lock; kernel/source generation proofs remain inside the transaction.

A candidate declaring `meet-runtime-v1` / `person-service` uses the restart-blocker census: rooms owned by a successfully connected independent runtime do not block that host's publication. Their process, Chromium and external meeting state remain in the person's service cgroup through supervisor activation. The first upgrade from in-process rooms still waits once on that host; an unknown runtime or census remains an explicit deferral, not permission to kill a meeting.

A repairable failure retains `repairs/REQUEST/receipt.json`, prompt, Pi session, agent log and `result.json`. Cancellation creates no repair authorization: launch, result acceptance and continuation recheck the stop, while outstanding host restoration remains owned. The dedicated `pi-stack-publication-repair@REQUEST.service` uses the configured Pi CLI and a registered source-only writer with 2 GiB headroom and 512 MiB growth. It acquires and verifies the failed source's immutable ref before workspace admission; later attempts start from the latest retained repair source. Product builds, Converge's minimal changed-source checks and post-serving diagnostics remain with their publication lanes.

An accepted `source-fixed` result pushes its immutable repair ref and invokes `continue-source REQUEST SHA SOURCE_REF REPAIR_ID` on the same request. [`deploy/publication-continuation.mjs`](../deploy/publication-continuation.mjs) preserves the original source identity, prior integration/check/artifact/host/failure evidence in `integrationHistory`, and causal repair refs in `repairSources`; the repaired exact source becomes the candidate of that same request, with builds and checks following the host-specific delivery policy. Continuation requires exact accepted repair evidence, original-source and retained-owner ancestry, and restored unfinished host custody. It does not create a new request or erase the failure history. An `infrastructure-fixed` result permits one evidenced unchanged-source retry, with explicit custody reconciliation. A `deliveryOwnerSourceSha` binds a retained, installed descendant controller repair without changing the product candidate: only failed host lanes receive that immutable controller, while successful peer outcomes and candidate identity remain intact. Product-changing `ownerSourceSha` requires explicit same-request source continuation, with host-specific builds and checks. Final consumer equivalence proofs run from the retained Git source repository, not an installed component that lacks source history. Repeated defects and interrupted repairs remain assigned with their evidence. After completing an interrupted repair's existing workspace/result, `deploy/publication repair-result REQUEST` accepts that same inactive service's result once. `deploy/publication repair REQUEST` adopts a failed request lacking repair custody.

An explicitly declared host `phoneConfigurationCandidate` is validated during preparation while the serving Phone configuration and its active-call census remain canonical. Its owner-only bytes are installed atomically only after the new accepting supervisor is ready; a revision-bound private receipt under `/var/lib/pi-stack/phone-configurations` retains exact configuration rollback custody. Changed candidate or canonical generations refuse activation or rollback. Phone activation follows the phone unit's bound personal supervisor without unlocking it. An inactive owner leaves calling stopped; an active owner restarts calling. Reset failure/start-limit state only when the phone itself is failed: querying an inactive unit can load it transiently, then systemd can unload it before `reset-failed`. Transitioning phone or supervisor state defers activation; failed/unknown owner state and unknown phone state reject explicitly. `scripts/deploy-phone.test.mjs` isolates host reservations and covers failure reset, unloaded inactive units and these state transitions.

Focused checks:

```sh
node --test scripts/publication-adoption.test.mjs scripts/publication-config.test.mjs scripts/publication-roots.test.mjs scripts/publication-proof.test.mjs scripts/publication.test.mjs scripts/publication-gate.test.mjs scripts/publication-source.test.mjs scripts/publication-meetings.test.mjs scripts/publication-progress.test.mjs
```

Publication fixtures never acquire capacity from the host's live authority: Orchestrator setup removes inherited capacity settings and points at a missing manifest in its temporary home. Missing-configuration tests select their own absent absolute manifest. Browser-doctor preflight fixtures use an explicit unmanaged test owner and never call the host's live capacity authority. Host-deployment fixtures provide an explicit synthetic readiness receipt and exercise both initialized and uninitialized gates.

## Release checkout ownership

Host release wrappers use [`deploy/release-checkout`](../deploy/release-checkout), not an editable working tree. Install that reviewed helper as `~/machine/pi-stack-release-checkout` and source it from the host's release wrapper. The wrapper selects the submitted committed source in `~/.local/state/pi-stack-release/repository` and runs [`deploy/prepare`](../deploy/prepare) and [`deploy/host`](../deploy/host) under its explicit release mode. Host-specific diagnostics run after serving. The publication target's `releaseRepository` must name that same release-owned checkout.

`pi_stack_select_release_checkout STATE REPOSITORY COMMIT LIVE_MARKER ALLOW_ROLLBACK` takes the shared `/srv/pi/.pi-stack-deploy.lock`, selects detached HEAD and holds host, state and checkout locks through preparation and activation. Direct component deployments and preparation use the same lock order. The requested commit must descend from both the selected checkout and the live marker unless the host explicitly authorizes rollback. An unexpected origin or dirty release-owned checkout fails without discarding changes. Recover unique edits into their source owner before retrying. A writable source checkout's index and branches are never reset by the release wrapper.

A publication also owns `/srv/pi/.pi-stack-deploy.lock.publication`, a root-owned JSON reservation containing its request ID and integration SHA. It is created and removed under the host lock, with restoration intent recorded first in the request's `reservations` field. It protects that host's artifact installation, activation and proof from a competing release, then is removed as soon as durable host delivery is proved. Waiting for another host must not keep the successful host reserved; a newer admitted publication can advance it. The owner passes `PI_STACK_PUBLICATION_REQUEST` to its wrappers; source selection, preparation and component deployment require both that identity and the reserved SHA. Other deployments exit 75 without selecting source. A matching request may recover its own reservation idempotently, never another request's. `PI_STACK_HOST_LOCK_PATH` relocates both lock and reservation for fixtures. Keep installed host release-checkout helpers current when upgrading this protocol; copying the reviewed helper needs no service restart. The worker/watchdog recover recorded reservation custody, so do not clear receipts or remove a reservation to force a competing release through.

The release checkout and its ignored dependencies are reproducible. `node_modules` is ignored at every depth as either a directory or a symlink; never commit it. A directory-only ignore let a writer's dependency symlink enter source, and installation replaced that tracked link with a directory, blocking the next release as dirty (PUB-bdcfabc30fecf8bed025a2f5). The release-checkout tests cover both forms and reject tracked dependencies. Retain its state while a release holds locks; remove it only after checking for unique source work and running releases. The next wrapper recreates it from its configured remote. `node --test scripts/deploy-lock.test.mjs scripts/release-checkout.test.mjs scripts/publication-reservation.test.mjs` covers locks, publication reservation recovery and source isolation in seconds.

## What a host provides

Every host supplies Unix people, a host file and systemd services. The host file at `/etc/pi-stack/host.json` names a `fleetUser`, its endpoint catalog and optional extra packages and skills. This is a fictional example, not a production host file:

```json
{
  "version": 1,
  "fleetUser": "operator",
  "environments": [
    { "id": "home", "name": "Home" },
    { "id": "studio", "name": "Studio", "upstreams": { "alice": "http://127.0.0.1:19000" } }
  ],
  "packages": [],
  "skills": []
}
```

The fleet deployment provisions `/var/lib/pi-stack/model-availability` owned by `fleetUser`, mode 0755, and preserves its `policy.json` contents with mode 0644. Every person can read the [global new-thread model policy](threads.md#model-availability), but only the administrator can atomically replace it. Rehearsals override `PI_STACK_MODEL_AVAILABILITY_PATH` and do not provision production state. Policy changes refresh every supervisor's start profiles and subscribed dashboard without restarting threads.

`environments` is the router's endpoint catalog. The local entry has no `upstreams`; remote entries map each granted Unix person to that person's supervisor origin, not another router. Those origins have no credentials, paths, queries or fragments. `PI_STACK_HOST_FILE` selects a different file for a fixture. Restart the router after changing its catalog. Persons live separately in `/var/lib/pi-remote/persons/<user>.json`, managed by `pi-remote person add` and `pi-remote person update USER` with JSON on stdin. The person writer preserves supervisor-readable permissions, including for locked people. `deploy/account USER` onboards a registered Unix account against the selected release. [Person timezone host transport](person-timezone-host.md) owns narrow per-account projection paths, memory-only reader grants and Remote-before-fleet activation; no private mount is added for timezone metadata.

[`deploy/systemd`](../deploy/systemd) contains reference units for the router, supervisors, Orchestrator, Voice and Meet recognition. A host installs those references or declares matching units with its own package paths. Voice loads its OpenAI credential from root-owned `/var/lib/pi-stack-voice/openai-api-key` through systemd `LoadCredential`; deployment does not provision it. The Voice service owns its lease database under `/var/lib/pi-stack-voice-runtime`. Supervisors select its loopback endpoint with `PI_STACK_VOICE_URL`. No browser client receives the key.

External Meet transcription uses raw English Nemotron recognition on the ONNX INT8 CPU encoder. [`deploy/meet-recognition`](../deploy/meet-recognition) prepares its Python environment, pinned weights and source; [`deploy/meet-recognition-service`](../deploy/meet-recognition-service) activates `pi-stack-meet-recognition.service`. The `Type=simple` unit becomes active before model loading finishes. Activation therefore allows 40 seconds for its loopback listener, stops immediately if the unit exits, and includes service diagnostics on failure. Publication selects the prepared recognition tree; activation starts its service concurrently with Voice and Remote handoff. Failed or interrupted deployment restores the prior selection and previous service state without waiting for another cold start. `node --test scripts/meet-recognition-service.test.mjs scripts/meet-recognition-host.test.mjs scripts/meet-recognition-retain.test.mjs` covers readiness, overlap, rollback and retention.

The engine's loopback port 8797 is UID-gated to root and the administrator. Ordinary supervisors reach `/v1/meet/recognition` through their UID-gated person broker. External meeting audio enters the person's durable transcript queue through the authenticated Remote router; the recognizer consumes that queue. Keep the engine listener off the LAN. Recognition environments use `uv --link-mode copy`, keeping service library permissions independent of installer-cache permissions.

## Browser prefix hosting

Publish the router at `/` or a directory prefix. For `/pi-stack/`, redirect `/pi-stack` to `/pi-stack/` with its query string, strip `/pi-stack` when proxying requests to the router, and apply the host's access policy to the whole prefix. Keep OAuth cookies and the callback under the same prefix if using [company browser sign-in](../apps/remote/README.md#company-browser-sign-in). The [shared client](../apps/remote/web/README.md#browser-mount-path) derives its mount from the page URL. Do not publish supervisor ports or create root-level aliases around the router.

## Gateway access and host boundaries

A person registry's `remoteAccess` lists allowed environment IDs. Omitting it grants only this host's endpoint. A remote grant requires that person's encrypted-folder identity and an upstream mapping. The router authenticates `POST /v1/unlock`, then sends only that person's allowed same-origin `/v1/remotes/<id>` endpoints through `GET /v1/environments`. Client person hints do not authenticate requests. The router rechecks the person's grant for every forwarded request and removes client authentication before reaching the remote supervisor. Bind private listeners to loopback and enforce host UID gates for the gateway, root deployment and each owning service. Host-owned SSH tunnels forward to a matching remote supervisor, never a shared router.

### Caller identity at supervisors and Orchestrator

Supervisors and Orchestrator daemons verify who creates threads and who sends as a thread; the [unified-thread contract](threads.md#caller-identity) owns the rules. Two host file keys configure it; both are optional:

- `upstreamCredentials`: SHA-256 hex digests of the credentials other hosts' routers present when they forward a person to a supervisor on this host. Each router creates its credential for environment `<id>` on first use at root-only `/var/lib/pi-remote/upstream-credentials/<id>` (`PI_REMOTE_UPSTREAM_CREDENTIAL_DIR` for fixtures) and sends it as `x-pi-remote-upstream`. Install its digest on the upstream host with `sudo sha256sum < /var/lib/pi-remote/upstream-credentials/<id>`, then restart that host's supervisors. Without a listed digest, forwarded requests reach the supervisor as ordinary local processes and cannot create a person's conversation or name a parent.
- `meetingCensus`: an optional command list for meetings a host service owns outside Pi Remote, such as a calendar bot waiting in a lobby that has no room yet. [`deploy/meeting-census`](../deploy/meeting-census) runs it as root with a 20-second limit. Each stdout line is one live meeting. A non-zero exit is unknown state and holds the restart like a live meeting.
- `releasePrerequisites`: optional objects with `name`, `piStackSource`, `nativeSource` (full Git SHAs), `statusSocket` (the native runtime's Unix `/status` endpoint), and `nativeRepository` (its local Git checkout). When the Pi Stack candidate descends from `piStackSource`, [`deploy/native-prerequisites`](../deploy/native-prerequisites) requires the selected runtime's `.source.commit` to descend from `nativeSource`. The host checks this before build or activation; the publication owner probes every 30 seconds without burning attempts or restarting services, then resumes once the native source is serving. An unavailable or malformed source/status is a real failure, never interpreted as satisfied. Converge declares the Kenan voice dependency in its Terraform-owned `/etc/pi-stack/host.json`; keep this declaration synchronized when changing the native API.
- `callerAttestation`: a command list run with a local caller's pid appended when that process creates a thread. Its JSON output is stored as `metadata.createdBy.attestation`, so host policy can classify the thread later from what was true when it was created.

Each person's thread capability key is created on first use at `~/.local/state/pi-stack/thread-capability.key` (mode 0600, `PI_THREAD_CAPABILITY_KEY` for fixtures). Deleting it invalidates every running session's `PI_THREAD_TOKEN` until the session reopens.

`deploy/smoke` checks router authentication, static assets, active supervisor health, Voice and transcription. For a key-bootstrap host, it reads existing root-only `/run/pi-remote-keys/<user>` credentials through a pipe and unlocks only people already open. `PI_REMOTE_KEY_DIR` selects a fixture directory. For an OAuth host it checks unauthenticated rejection and probes supervisors as root; a real browser sign-in is a post-serving diagnostic. ### Release retention

[`deploy/retain`](../deploy/retain) bounds the release store; `deploy/prepare` runs it before every release. Per component it keeps the selected release and the `PI_STACK_RELEASE_KEEP` (default 5) most recently published others for rollback. It also keeps any release that a live process names (cwd, executable, command line, environment, mappings or open files), any release that was selected when a still-running Pi process started, any release an unfinished Orchestrator run records in an account ledger, and anything published within `PI_STACK_RETAIN_GRACE_SECONDS` (default one hour). A dependency tree under `/srv/pi/dependencies` stays while a kept release links into it or a process names it. Retired entries are renamed to `.retired.*` before removal, so a half-deleted release is never selectable, and a later run finishes any removal an interrupted one left. An unreadable ledger stops retention with nothing removed. Historical usage remains untouched. An unpublished upstream Pi commit may be carried in [`vendor/pi`](../vendor/pi/README.md) with its source provenance. ## Serving outcomes and post-serving diagnostics

- Each host delivery records its exact submitted candidate and matching artifact hashes. Component markers carry that candidate SHA. Source-equivalent unchanged owners can retain their running revision; changed source cannot borrow an old process identity. A later branch update neither changes the in-flight candidate nor requalifies local delivery.
- kenan-server's `immediate` lane records builds and actual service-start/recovery outcomes, without tests, doctors, smoke, warm-up or browser gates. Converge's independent `minimal` lane records changed-source builds and actual service/source health. Each successful host releases its reservation immediately; failed hosts receive bounded automatic retry and an alert. A remote wait or failure never delays or rolls back local serving.
- Full checks, Android native tests, runtime doctors, host proofs and smoke run after that host serves under durable post-serving custody. Report passed, failed, deferred or not-run outcomes truthfully; a source marker is not a passing diagnostic. Failed diagnostics alert without altering serving state. Passing native-test receipts qualify future APK reuse, not the current delivery.
- Private folders, credentials, UID gates and per-person access remain unchanged. Locked people remain locked; publication does not unlock them or enable Root Kenan. No direct supervisor or development-web route bypasses the router. Accepted jobs and active runtimes keep their recorded execution custody through handoff.
- Native-history reservations and forward-only migration boundaries remain explicit until their own restoration or serving transition finishes. Neither a successful peer nor a diagnostic failure erases that custody. Reports distinguish each host's delivery, recovery and check outcomes rather than requiring fleet-wide green before serving.
