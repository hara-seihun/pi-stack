# Deployment

Pi Stack separates reviewed source from host-owned accounts, credentials, network routes and release paths. This guide describes the shared deployment contract. A host handbook owns its actual values and acceptance receipts.

## Native history migration

Publication observes the [native history boundary](native-history-boundary.md) before selecting new artifacts. Old owners continue accepting new agents, messages, questions and scheduled wakes while their work runs. A naturally idle owner uses a short dispatch-only replacement; normal receipt identities survive transient listener replacement. Each owner migrates inside its retained private namespace after its old writers close. Locked owners use the same preserving first-unlock transform. Preserve the [migration](native-history-migration.md)'s private snapshots/preimages in backup coverage. New databases use native history directly.

## Host platforms

The maintained publication owner runs on an Ubuntu 26.04 local server and releases the same integration to that server and a Debian 12 remote VM. External Meet transcription uses the CPU-only [Meet recognition service](../apps/meet-recognition/README.md), declared by each host.

Ubuntu and Debian provision packages and systemd units through their host handbooks. NixOS remains a supported host arrangement: declare equivalent packages, units and access gates in its configuration, then activate its generation through that host's handbook. NixOS activation commands do not apply to Ubuntu. Public source does not own machine names, SSH aliases or filled-in target configuration. Preserve publication target IDs across host replacements while receipts still carry custody.

## Publication owner

From a writer checkout, submit an immutable commit:

```sh
deploy/publication submit "$(git rev-parse HEAD)"
```

Before it pushes the immutable request ref, `submit` fetches current `main` and refuses a source commit with any Git root absent from that branch. Merging current `main` into a checkout with another root does not make it safe: replay the intended changes onto current `main` instead. A shallow checkout or grafted history cannot prove this ancestry and is rejected. The gate protects the request ref as well as the later integration push. Submission also requires ancestry of the installed owner's retained `refs/pi-stack-publication/owner-source` before pushing the immutable ref or accepting queue custody; an omitted bootstrapped repair is a source-admission error, not a late deployment attempt.

The receipt acknowledges durable custody. The owner integrates the source with `main`, checks changed inputs once, then delivers independently to each configured target. Successful individual check jobs persist outside the disposable checkout in `check-cache`; a failed sibling does not discard them. Keys include declared source/dependency inputs, command arguments, explicit job environment and toolchain identity. Unknown job scopes, corrupt receipts and changed inputs refuse reuse. Output-producing jobs still run through their own source/output-hashed build receipts. `PI_STACK_CHECK_CACHE_DIR` enables this path; without it `npm run check` runs every check. The `scripts/check-cache.mjs seed CHECKED_ROOT REQUEST_JSON CACHE_DIRECTORY` maintenance command imports only positively completed stages from the exact clean checked source on the same toolchain boot, never failed or incomplete stages. Checkout cleanup preserves owned build/Gradle outputs; their hashes—not their mere presence—determine eligibility. Remote builds once and Kenan copies that checked shared web output rather than running Vite again. Android has a separate native-check receipt, so an unrelated later failure does not invalidate its finished proof. Checkout-manager filesystem fixtures run under `tools/agent-workspace/check.mjs` in that tool's own validation/adoption path; they are not application release dependencies. The application gate still checks the source manifests and its use of tool contracts. On each ready host it prepares immutable components while the old controllers serve, performs the accepting controller handoff, then installs and verifies the matching Android/web artifact, records durable delivery proof and releases that host's reservation. Meetings, native prerequisites, locks or failures on one host never hold another ready host or its matching artifact. A waiting or failed target retains its own outcome and recovery custody; successful delivery elsewhere is neither undone nor replayed. Full publication success still requires every target to have the requested source or a checked descendant, with valid matching artifacts. `deploy/publication inspect REQUEST` shows progress. Submitting the same source SHA returns its receipt or rejects an unrepaired failure. `deploy/publication cancel REQUEST` records cancellation for the next command boundary; it does not kill an in-flight deployment or undo a completed host release.

[`deploy/publication-bundle.mjs`](../deploy/publication-bundle.mjs) freezes ready, untouched queued sources into one hash-bound cohort before work begins. One fetch and ancestry-preserving integration produces one checked revision and immutable Android/web artifact for the cohort. Every member retains its source ref, requester, repair history and independent host delivery receipts; followers reuse only passing, already integrated source/check/artifact evidence, never another request's reservations, maintenance or native-history custody. A partially written cohort repairs its member bindings on restart. Running requests, previous attempts, repair submissions, waits, explicit live-meeting overrides and requests with host effects are not coalesced. A source/check failure retains each member's causal failure without retrying unchanged source; a host failure or wait does not invalidate passing source evidence for peers. Prepared immutable artifacts remain available after completion for cohort consumers.

Install the local owner with `deploy/publication install` after creating `/etc/pi-stack/publication.json`. The installer copies the command and its modules to the configured `paths.installedCommand`, renders its seven systemd units in `paths.userUnitRoot`, reloads the user manager and enables the wake path and timers. It does not restart the active worker. On a successful release, the worker verifies the integration checkout's HEAD and runs that checkout's `deploy/publication install` under its existing worker lock, never installing from the mutable writer checkout. The candidate owns its module list and installation logic: a bootstrapped owner must not require its own dependencies in a different release. This prevents the missing `meeting-census` adoption failure observed when a meeting-wait repair reached the owner before its source reached an unrelated publication. Repair descendants retain that repair's source as well as the requested change. Coordinate a manual owner upgrade with any in-flight worker before changing its watchdog. A repair that must reach the owner before its own release can use `deploy/publication install --code-only`: this takes the worker lock nonblockingly and atomically installs the command and modules without rewriting units, waking services, submitting source or retrying requests. A busy worker rejects that bootstrap. Code-only installation requires committed deployment source and an initialized publication repository; before copying code it retains that commit at `refs/pi-stack-publication/owner-source` in the publication repository. Integration (before full checks), checked-integration reuse, owner adoption and subsequent installation require this retained commit's ancestry, preventing an unrelated release from erasing a bootstrapped repair. If source is missing, merge the named local ref into an authorized publication source; the worker never merges or republishes cancelled work implicitly. The normal successful release still adopts its checked owner. This source-custody gate was added after a later installation removed the cancellation repair and automatically dispatched a repair for another cancelled release.

[`config/publication.example.json`](../config/publication.example.json) shows the schema. Set:

- `repositoryUrl` to the canonical Git origin and `mergeAuthor` to the name and email for integration commits.
- `targets` in attempt order, not as an all-host readiness barrier. Each has a stable receipt `id`, an expected supervisor `environmentId`, an SSH alias or `null` for the sole local target, absolute `releaseCommand`, `releaseRepository` and `checkServicesCommand` paths, a `hostConfig` path, `requiredUnits`, and a loopback `voiceStatusUrl`. Remote targets also specify an absolute writable `androidTransferRoot`.
- `paths` for the publication user's canonical checkout, ignored Android `local.properties`, state directory, installed command, user unit directory, repair workspaces, Pi CLI and alert inbox. Omitted paths use home-relative defaults, except for the alert inbox.

The file contains host identities and routes, not credential values. `PI_STACK_PUBLICATION_CONFIG` selects a different file for a fixture. Provision it before either installation or submission. Keep target IDs stable while receipts carry maintenance or restoration custody. The target's host file supplies `fleetUser`. Its installed `checkServicesCommand` checks the router, failed runtime units, fleet service and every unlocked supervisor's unit. Runtime failures cover all Orchestrator and Remote instances (including locked people), router, Voice, Meet recognition and model brokers. Other failed `pi-*` units are reported on stderr and retained as `otherFailedPiUnits` in the final host proof, not treated as release dependencies. The host's `requiredUnits` adds any host-specific dependencies. A scheduled Claude balance collector failure caused an otherwise healthy release to be rejected on September 29; maintenance failure must remain visible to its host owner without vetoing an application release. Publication then checks each unlocked supervisor's health, commit and environment ID, along with the configured required units and Voice status. It does not assume any named person is unlocked. The remote SSH user must already have release authority. Its credential and Android signing key remain in host custody.

The worker's state is under `paths.stateRoot`, by default `~/.local/state/pi-stack-publication`. Requests are `queued`, `running`, `failed` or `published`. A busy first-activation gate returns to `queued` with `blockedSince`, `waiting.reason` and `nextAttemptAt`. Cancellation is a failed request with reason `cancelled`. Requests and repair receipts are the issue source of truth. `deploy/publication issues` reads their complete index without taking the worker lock, so inspection remains available during a release. The owner maintains one bounded alert at the configured inbox; `acknowledge-issues` silences the current notification without clearing repair or host custody. Each request retains durable successful host outcomes while waiting elsewhere. Its final proof combines those receipts with fresh proof of any already selected checked descendant, including a descendant delivered by another still-waiting publication. Issue resolution names complete publication ancestry, receipts and proofs even after a source-root cutover. Request completion requires a qualifying outcome for every configured target. Retain those Git objects in the publication repository. Unrelated source remains unresolved, and outstanding host restoration always remains an issue.

Chat reports and Machine alerts derive their current outcome from the same repair/ancestry resolution view. Routine repair progress does not replay a failure; a successor owns its inherited requester's completion. If a combined publication resolves another requester's source, that requester receives a success report naming the deployed proof while the original failed receipt remains unchanged.

To report back to a Remote thread, set `PI_STACK_PUBLICATION_REPORT_URL` and `PI_STACK_PUBLICATION_REPORT_SESSION` when submitting. `deploy/publication report REQUEST REMOTE_URL SESSION_ID` attaches a requester to an earlier request; without arguments, it reconciles an existing report only. `report.status: accepted` means Remote queued the report. `delivered` means its thread confirmed dispatch. Notices retry transport separately from release work. Submission validates the requester identity without probing its availability: an offline or retired requester cannot prevent custody transfer, including a repair successor. Notification failure remains in the report receipt; it is not deployment failure.

### Ancestry and live handoff

Source integration and checks belong to the immutable request or queued-source cohort; readiness, ancestry, reservation and handoff belong to each request's host delivery. Before changing that host's intake or selecting source, the owner reserves it and checks that the candidate descends from its selected live commit and release-checkout HEAD. Missing selected source is fetched by exact SHA from its configured `releaseRepository` and retained under `refs/pi-stack-publication/selected/<sha>`. The ancestry proof names the host and baseline; each wrapper repeats the check under its deployment lock. A divergent candidate requires a checked repair descendant containing the missing history, not disabled rollback protection.

A newer checked request may roll a ready host forward while an older request waits elsewhere. If that host already serves a checked descendant containing the older request's source, the older request accepts its durable host and matching-artifact proof instead of deploying an ancestor or requiring its original exact integration SHA. Different targets may therefore finish a request at different checked descendant SHAs; unrelated source or a source-only proof never satisfies delivery.

`unified-threads-v1` has a per-host first-activation gate. For the host being activated, the worker records its fleet launch state, pauses new launches, waits for active runners and fleet work, then freezes its router, supervisors and pre-contract owner for a final census. Busy hosts are restored and retried without replaying accepted work. The recorded operator pause remains paused. An empty census permits the release wrapper to transfer native transcript references, held messages and pending results. Later releases use live controller handoff without the first-activation pause. A target that already selected the thread contract cannot be replaced by code without it.

Failure or cancellation restores recorded intake and service states for unfinished host work; it does not undo a proved successful delivery. Unrestored native-history custody is a per-host admission lease even when its transient deployment reservation was released. Before reserving a target, publication reads every other request's native-history receipt; any state other than positively `restored` or `released` produces a `native-history-custody` wait naming the original request and receipt. Failed or cancelled request status does not release that lease. Successors and unrelated checked requests cannot reserve, census, advance native fences, install artifacts or activate on that host. Their wait probes read publication custody only. Clearing one host permits that host alone to proceed; the original owner retains its other hosts until their restoration or serving-native release is acknowledged. Checks/builds and independently free hosts continue normally.

Each host reservation spans only that host's ancestry census, artifact installation, activation and proof. The owner releases it immediately after durable proof, or after restoring custody on deferral or failure. Interruption recovery is likewise per host. Unfinished restoration remains explicit custody and prevents another deployment to that host until repaired, without blocking other ready hosts. Checked integration and artifacts remain reusable for remaining targets; a new source integration requires its own checks. The owner never force-pushes, deploys an unchecked merge or downgrades a successful host because `main` moved. Per-target delivery outcomes, host proofs, Android hashes and source refs stay with the request across waits, failures and retries.

## Publication progress and repair

[`deploy/publication-control.mjs`](../deploy/publication-control.mjs) owns command deadlines and retry budgets. Each subprocess records its arguments, directory, start, deadline and log before launch. The independent watchdog records a stalled running command and stops its cgroup. Queue supervision instead tracks one request's receipt revision and retry schedule across continuous watchdog observations. A meeting or native-source probe, a different queue head, or a supervision gap resets its claim budget. Before failing an unclaimed request the watchdog takes the worker lock and rechecks the receipt; it never stops a worker just because a queued probe owns that lock. Deployment locks and first-activation gates have bounded retry budgets. A live meeting, host-declared native source prerequisite or busy old native history generation is an external dependency: the affected target waits, releases its host publication reservation and retains checked artifacts. Every 30 seconds the worker makes a bounded, read-only probe without rerunning preparation or consuming deployment attempts; a legitimate busy dependency has no wait deadline. Census and native-source errors are never treated as readiness. A census failure retains its probe error and reaches failure only after `policy.meetingProbeFailureLimitMs` (two hours) of consecutive failures. Native-source and native-history probe errors fail the affected host immediately; only their explicit marked exit-75 dependency outcomes remain waiting. The receipt preserves the causal wait/probe, exit status and command, and creates dedicated repair custody without rerunning preparation when no peer has deliverable work. Newly ready peers still finish independently before the request becomes terminal. A failed native-history probe does not establish safe native-schema rollback: its maintenance custody becomes `repair-required`, excluding automatic restoration and preserving its immutable source and causal probe. After repairing closure/source custody, `deploy/publication recover-native-history REQUEST HOST` takes the worker lock and explicitly invokes the frozen boundary's bounded `--restore` for that target; refusal keeps that state and records the recovery error. Successful restoration records `restored` without retrying or editing the original failure/repair receipt. Failed/interrupted ordinary restoration also retains the original failure and repair receipt rather than replacing them with a new repair chain. The existing repair owner then accepts `result.json` through `repair-result REQUEST`; source-fixed results submit one causal descendant, while infrastructure-fixed results permit one evidenced unchanged-source retry. Other ready targets still receive their artifact and server release. Deferred work cannot monopolize queue intake: newer checked requests may deliver to ready hosts while remaining targets wait. When the dependency clears, only unfinished delivery resumes, accepting a newer descendant's proof where available. Cancellation, command deadlines and actual deployment failures retain their explicit handling and repair evidence; retry never discards completed target outcomes.

An explicit `STATE/always-open-source-hold.json` suspends worker draining and automatic retry/wake, not source intake or dedicated repair custody. Its version-1 contract requires nonempty `reason`, owning `threadId` and `releaseWhen`, with `applicationStop:false`. The watchdog exposes the hold in `worker-watch.json`, discards queue claim clocks while held and starts a fresh clock after the owner releases it. A malformed hold rejects execution. Running-command deadlines remain supervised; explicit restoration remains available. Only the hold's owner removes it after its release condition is satisfied.

A restored old-owner maintenance receipt is not reused as a new attempt. The successor's source-bound helper validates the previous acknowledged identity, absence of thread closure/admission fences and native readiness, and the exact owner ledger. An already prepared fleet barrier must belong to this new candidate; foreign custody refuses acquisition. It then creates a source-bound observation receipt, retaining the prior restoration receipt as evidence. Observation keeps ordinary intake and scheduled wakes open. Same-attempt recovery does not rewrite receipts or reacquire a restored attempt. Health checks execute before and after fence transactions, never while holding a live consumer's SQLite write lock; kernel/source generation proofs remain inside the transaction.

A candidate declaring `meet-runtime-v1` / `person-service` uses the restart-blocker census: rooms owned by a successfully connected independent runtime do not block that host's publication. Their process, Chromium and external meeting state remain in the person's service cgroup through supervisor activation. The first upgrade from in-process rooms still waits once on that host; an unknown runtime or census remains an explicit deferral, not permission to kill a meeting.

Each new repairable failure gets `repairs/REQUEST/receipt.json`, a saved prompt, Pi session, agent log and `result.json`. Cancellation is terminal, not a repairable defect: neither failure handling nor watchdog adoption creates a repair for it. The watchdog blocks idle repair work mistakenly assigned before cancellation was recognized, preserving its evidence; an active agent may finish, but its result cannot submit a successor or retry. Repair launch, result acceptance, submission, enqueue and retry recheck the cancellation marker or recorded cancellation reason. Host restoration remains the worker's responsibility even after cancellation. The local `pi-stack-publication-repair@REQUEST.service` uses the configured Pi CLI and a registered writer workspace, not the paused fleet. Before workspace creation the repair owner acquires the request's canonical immutable source ref into its release-owned repository and verifies its commit against the receipt. Existing retained custody must match; mismatched refs or commits refuse preparation. This happens even when the worker never claimed the queued request, so local clone admission can resolve the source SHA. Workspace creation selects the failed source SHA explicitly and declares source-only admission with 2 GiB operating headroom and 512 MiB growth; it does not reserve an unestimated full build alongside the publication worker. Its 40-second creation deadline fits the parent's 45-second budget. Full builds and checks remain with the publication worker. A `source-fixed` result submits a new descendant commit with `--repair-of REQUEST`; an `infrastructure-fixed` result grants one unchanged-source retry with evidence. An irrecoverable or interrupted repair remains assigned with its evidence. After manually completing an interrupted agent's existing workspace and `result.json`, run `deploy/publication repair-result REQUEST`; it checks service inactivity and hands off that same result once. `deploy/publication repair REQUEST` adopts a failed request predating the repair-policy activation. Inspect the named receipt before either command.

Phone activation follows the phone unit's bound personal supervisor without unlocking it. An inactive owner leaves calling stopped; an active owner restarts calling. Reset failure/start-limit state only when the phone itself is failed: querying an inactive unit can load it transiently, then systemd can unload it before `reset-failed`. Transitioning phone or supervisor state defers activation; failed/unknown owner state and unknown phone state reject explicitly. `scripts/deploy-phone.test.mjs` isolates host reservations and covers failure reset, unloaded inactive units and these state transitions.

Focused checks:

```sh
node --test scripts/publication-adoption.test.mjs scripts/publication-config.test.mjs scripts/publication-roots.test.mjs scripts/publication-proof.test.mjs scripts/publication.test.mjs scripts/publication-gate.test.mjs scripts/publication-source.test.mjs scripts/publication-meetings.test.mjs scripts/publication-progress.test.mjs
```

Publication fixtures never acquire capacity from the host's live authority: Orchestrator setup removes inherited capacity settings and points at a missing manifest in its temporary home. Missing-configuration tests select their own absent absolute manifest. Browser-doctor preflight fixtures use an explicit unmanaged test owner and never call the host's live capacity authority. Host-deployment fixtures provide an explicit synthetic readiness receipt and exercise both initialized and uninitialized gates.

## Release checkout ownership

Host release wrappers use [`deploy/release-checkout`](../deploy/release-checkout), not an editable working tree. Install that reviewed helper as `~/machine/pi-stack-release-checkout` and source it from the host's release wrapper. The wrapper selects committed source in `~/.local/state/pi-stack-release/repository`, runs [`deploy/prepare`](../deploy/prepare) and [`deploy/host`](../deploy/host), then checks host-specific invariants. The publication target's `releaseRepository` must name that same release-owned checkout.

`pi_stack_select_release_checkout STATE REPOSITORY COMMIT LIVE_MARKER ALLOW_ROLLBACK` takes the shared `/srv/pi/.pi-stack-deploy.lock`, selects detached HEAD and holds host, state and checkout locks through preparation and activation. Direct component deployments and preparation use the same lock order. The requested commit must descend from both the selected checkout and the live marker unless the host explicitly authorizes rollback. An unexpected origin or dirty release-owned checkout fails without discarding changes. Recover unique edits into their source owner before retrying. A writable source checkout's index and branches are never reset by the release wrapper.

A publication also owns `/srv/pi/.pi-stack-deploy.lock.publication`, a root-owned JSON reservation containing its request ID and integration SHA. It is created and removed under the host lock, with restoration intent recorded first in the request's `reservations` field. It protects that host's artifact installation, activation and proof from a competing release, then is removed as soon as durable host delivery is proved. Waiting for another host must not keep the successful host reserved; a newer checked publication can advance it. The owner passes `PI_STACK_PUBLICATION_REQUEST` to its wrappers; source selection, preparation and component deployment require both that identity and the reserved SHA. Other deployments exit 75 without selecting source. A matching request may recover its own reservation idempotently, never another request's. `PI_STACK_HOST_LOCK_PATH` relocates both lock and reservation for fixtures. Keep installed host release-checkout helpers current when upgrading this protocol; copying the reviewed helper needs no service restart. The worker/watchdog recover recorded reservation custody, so do not clear receipts or remove a reservation to force a competing release through.

The release checkout and its ignored dependencies are reproducible. `node_modules` is ignored at every depth as either a directory or a symlink; never commit it. A directory-only ignore let a writer's dependency symlink enter source, and installation replaced that tracked link with a directory, blocking the next release as dirty (PUB-bdcfabc30fecf8bed025a2f5). The release-checkout tests cover both forms and reject tracked dependencies. Retain its state while a release holds locks; remove it only after checking for unique source work and running releases. The next wrapper recreates it from its configured remote. `node --test scripts/deploy-lock.test.mjs scripts/release-checkout.test.mjs scripts/publication-reservation.test.mjs` covers locks, publication reservation recovery and source isolation in seconds.

## What a host provides

Every host supplies Unix people, a host file and systemd services. The host file at `/etc/pi-stack/host.json` names a `fleetUser`, its endpoint catalog and optional extra packages and skills. This is a fictional example, not a production host file:

```json
{
  "version": 1,
  "fleetUser": "operator",
  "environments": [
    { "id": "home", "name": "Home" },
    { "id": "studio", "name": "Studio", "upstreams": { "alice": "http://127.0.0.1:19000" } }
  ],
  "packages": [],
  "skills": []
}
```

The fleet deployment provisions `/var/lib/pi-stack/model-availability` owned by `fleetUser`, mode 0755, and preserves its `policy.json` contents with mode 0644. Every person can read the [global new-thread model policy](threads.md#model-availability), but only the administrator can atomically replace it. Rehearsals override `PI_STACK_MODEL_AVAILABILITY_PATH` and do not provision production state. Policy changes refresh every supervisor's start profiles and subscribed dashboard without restarting threads.

`environments` is the router's endpoint catalog. The local entry has no `upstreams`; remote entries map each granted Unix person to that person's supervisor origin, not another router. Those origins have no credentials, paths, queries or fragments. `PI_STACK_HOST_FILE` selects a different file for a fixture. Restart the router after changing its catalog. Persons live separately in `/var/lib/pi-remote/persons/<user>.json`, managed by `pi-remote person add` and `pi-remote person update USER` with JSON on stdin. The person writer preserves supervisor-readable permissions, including for locked people. `deploy/account USER` onboards a registered Unix account against the selected release. [Person timezone host transport](person-timezone-host.md) owns narrow per-account projection paths, memory-only reader grants and Remote-before-fleet activation; no private mount is added for timezone metadata.

[`deploy/systemd`](../deploy/systemd) contains reference units for the router, supervisors, Orchestrator, Voice and Meet recognition. A host installs those references or declares matching units with its own package paths. Voice loads its OpenAI credential from root-owned `/var/lib/pi-stack-voice/openai-api-key` through systemd `LoadCredential`; deployment does not provision it. The Voice service owns its lease database under `/var/lib/pi-stack-voice-runtime`. Supervisors select its loopback endpoint with `PI_STACK_VOICE_URL`. No browser client receives the key.

External Meet transcription uses raw English Nemotron recognition on the ONNX INT8 CPU encoder. [`deploy/meet-recognition`](../deploy/meet-recognition) prepares its Python environment, pinned weights and source; [`deploy/meet-recognition-service`](../deploy/meet-recognition-service) activates `pi-stack-meet-recognition.service`. The `Type=simple` unit becomes active before model loading finishes. Activation therefore allows 40 seconds for its loopback listener, stops immediately if the unit exits, and includes service diagnostics on failure. Publication selects the prepared recognition tree; activation starts its service concurrently with Voice and Remote handoff. Failed or interrupted deployment restores the prior selection and previous service state without waiting for another cold start. `node --test scripts/meet-recognition-service.test.mjs scripts/meet-recognition-host.test.mjs scripts/meet-recognition-retain.test.mjs` covers readiness, overlap, rollback and retention.

The engine's loopback port 8797 is UID-gated to root and the administrator. Ordinary supervisors reach `/v1/meet/recognition` through their UID-gated person broker. External meeting audio enters the person's durable transcript queue through the authenticated Remote router; the recognizer consumes that queue. Keep the engine listener off the LAN. Recognition environments use `uv --link-mode copy`, keeping service library permissions independent of installer-cache permissions.

## Browser prefix hosting

Publish the router at `/` or a directory prefix. For `/pi-stack/`, redirect `/pi-stack` to `/pi-stack/` with its query string, strip `/pi-stack` when proxying requests to the router, and apply the host's access policy to the whole prefix. Keep OAuth cookies and the callback under the same prefix if using [company browser sign-in](../apps/remote/README.md#company-browser-sign-in). The [shared client](../apps/remote/web/README.md#browser-mount-path) derives its mount from the page URL. Do not publish supervisor ports or create root-level aliases around the router.

## Gateway access and host boundaries

A person registry's `remoteAccess` lists allowed environment IDs. Omitting it grants only this host's endpoint. A remote grant requires that person's encrypted-folder identity and an upstream mapping. The router authenticates `POST /v1/unlock`, then sends only that person's allowed same-origin `/v1/remotes/<id>` endpoints through `GET /v1/environments`. Client person hints do not authenticate requests. The router rechecks the person's grant for every forwarded request and removes client authentication before reaching the remote supervisor. Bind private listeners to loopback and enforce host UID gates for the gateway, root deployment and each owning service. Host-owned SSH tunnels forward to a matching remote supervisor, never a shared router.

### Caller identity at supervisors and Orchestrator

Supervisors and Orchestrator daemons verify who creates threads and who sends as a thread; the [unified-thread contract](threads.md#caller-identity) owns the rules. Two host file keys configure it; both are optional:

- `upstreamCredentials`: SHA-256 hex digests of the credentials other hosts' routers present when they forward a person to a supervisor on this host. Each router creates its credential for environment `<id>` on first use at root-only `/var/lib/pi-remote/upstream-credentials/<id>` (`PI_REMOTE_UPSTREAM_CREDENTIAL_DIR` for fixtures) and sends it as `x-pi-remote-upstream`. Install its digest on the upstream host with `sudo sha256sum < /var/lib/pi-remote/upstream-credentials/<id>`, then restart that host's supervisors. Without a listed digest, forwarded requests reach the supervisor as ordinary local processes and cannot create a person's conversation or name a parent.
- `meetingCensus`: an optional command list for meetings a host service owns outside Pi Remote, such as a calendar bot waiting in a lobby that has no room yet. [`deploy/meeting-census`](../deploy/meeting-census) runs it as root with a 20-second limit. Each stdout line is one live meeting. A non-zero exit is unknown state and holds the restart like a live meeting.
- `releasePrerequisites`: optional objects with `name`, `piStackSource`, `nativeSource` (full Git SHAs), `statusSocket` (the native runtime's Unix `/status` endpoint), and `nativeRepository` (its local Git checkout). When the Pi Stack candidate descends from `piStackSource`, [`deploy/native-prerequisites`](../deploy/native-prerequisites) requires the selected runtime's `.source.commit` to descend from `nativeSource`. The host checks this before build or activation; the publication owner probes every 30 seconds without burning attempts or restarting services, then resumes once the native source is serving. An unavailable or malformed source/status is a real failure, never interpreted as satisfied. Converge declares the Kenan voice dependency in its Terraform-owned `/etc/pi-stack/host.json`; keep this declaration synchronized when changing the native API.
- `callerAttestation`: a command list run with a local caller's pid appended when that process creates a thread. Its JSON output is stored as `metadata.createdBy.attestation`, so host policy can classify the thread later from what was true when it was created.

Each person's thread capability key is created on first use at `~/.local/state/pi-stack/thread-capability.key` (mode 0600, `PI_THREAD_CAPABILITY_KEY` for fixtures). Deleting it invalidates every running session's `PI_THREAD_TOKEN` until the session reopens.

`deploy/smoke` checks router authentication, static assets, active supervisor health, Voice and transcription. ### Release retention

[`deploy/retain`](../deploy/retain) bounds the release store; `deploy/prepare` runs it before every release. Per component it keeps the selected release and the `PI_STACK_RELEASE_KEEP` (default 5) most recently published others for rollback. It also keeps any release that a live process names (cwd, executable, command line, environment, mappings or open files), any release that was selected when a still-running Pi process started, any release an unfinished Orchestrator run records in an account ledger, and anything published within `PI_STACK_RETAIN_GRACE_SECONDS` (default one hour). A dependency tree under `/srv/pi/dependencies` stays while a kept release links into it or a process names it. Retired entries are renamed to `.retired.*` before removal, so a half-deleted release is never selectable, and a later run finishes any removal an interrupted one left. An unreadable ledger stops retention with nothing removed. A readable retired ledger without a `release_path` column pins nothing only when it has no queued, starting or running rows; unresolved active work still stops retention. Historical usage remains untouched. A failed retention is reported but does not fail the release. `deploy/retain --dry-run` prints what would be kept and why; `--keep N` and `--budget-seconds S` override the depth and bound one run. A rehearsal whose releases live outside `/srv/pi` never touches the host's dependency trees. To roll back further than the kept depth, redeploy the older commit; publication rebuilds its release. An unpublished upstream Pi commit may be carried in [`vendor/pi`](../vendor/pi/README.md) with its source provenance. Pi Remote's staged import check uses the production dependency tree, not a writer checkout, and checks the supervisor, router, person CLI, Voice and Meet adapter before service activation.

## Leaving live development

Live development uses optional `pi-remote-dev-web@USER.service` and `pi-remote-dev-supervisor@USER.service` units with `/etc/pi-stack/dev-remote-USER.env`. See [the development unit contract](../apps/remote/README.md#live-development) for installation and the package restoration on stop. A production release should not select the live checkout or its overrides.

When moving work from live development into a release, first commit the source checkout's useful changes and record its SHA. Fetch that SHA into the release writer, incorporate its content, and retain its ancestry if the final tree deliberately replaces it. Do not reset, clean or stash away unique source. End live meetings and save transcripts before a supervisor handoff. After the checked release is ready, stop the relevant per-person development instances with `systemctl stop pi-remote-dev-web@USER.service pi-remote-dev-supervisor@USER.service`. Confirm `ExecStopPost` restored the selected production package. Remove that person's `/etc/pi-stack/dev-remote-USER.env` only after stopping the units; remove any temporary source override in host service configuration and reload the manager. Do not restart `pi-remote@USER.service` just to leave live development, since it may own an active turn.

The host handbook owns package and systemd changes, a NixOS generation switch where applicable, ingress route changes and release wrapper invocation. Let the publication owner deliver the checked integration independently to each ready target; an already selected checked descendant satisfies the request with its own matching artifact and host proof. After release, check that Voice's effective unit has no development source override, the router serves the production frontend, host smoke and commit markers match, and no development unit owns the selected Pi package. Retire any direct supervisor or development-web ingress route; keep the router as the published API entrance.

## Browser recovery

If a loaded native browser extension and executable have different versions, replace the process after its work settles rather than changing a child shell's `PATH`. Interactive Pi can use `/reload` when its loader supports physical extension entrypoints; older processes must reopen their existing session. Remote adopts active turns and replaces their runtimes when they settle. Fleet recovery uses the recorded Orchestrator release and exact JSONL without replaying finished work. `abort` and `kill` are terminal actions, not dependency reloads.

```sh
pi-agent-browser-doctor
pi-agent-browser-doctor \
  --worker-release /srv/pi/.pi-stack-releases/orchestrator/COMMIT \
  --session-file /absolute/path/to/settled-session.jsonl
```

The [doctor](../packages/runtime/browser-doctor.mjs) checks both extension-loading phases, native registration, an interactive snapshot, screenshot, exact-byte download, and cleanup. It also selects static and dynamically injected cross-origin iframes by CSS, fills and reads back their inputs, and checks selected-frame evaluation using disposable loopback origins (`127.0.0.1` and `localhost`). It additionally attaches a second native session over CDP to the already-loaded probe iframe and verifies its snapshot, fill/readback and realm, covering initialization-time attachment events that local navigation alone cannot exercise. Its saved-session probe copies a settled JSONL to a temporary directory rather than modifying the canonical session or ledger. The isolated-script check covers open, snapshot and automatic cleanup; the remaining linear checks use fail-fast native batches through [`browser-probe.mjs`](../packages/runtime/browser-probe.mjs), with URL re-verification after evaluation. This avoids repeating wrapper/session-policy subprocesses for every command under the 20-second call and 50-second deployment deadlines. PUB-b624002f5cf5176d247a43b7 exhausted the former script budget after sixteen successful commands on a loaded Converge host. The batched doctor retains all checks, including remote attachment after frame creation, artifact verification and exact bytes. A failed probe retains its files and per-phase `browser-proof.json` results for diagnosis; success reports phase timings. `node --test packages/runtime/browser-probe.test.mjs` checks failed rows, incomplete batches, incorrect frame results, artifacts and cleanup without launching Chrome. ## Release verification

- For each target, `/srv/pi/pi-remote/.pi-stack-commit`, Orchestrator marker and Voice `/status.releaseCommit` agree on that host's delivered checked revision. It contains the requested source by ancestry; it need not equal another target's revision or the older request's original integration SHA.
- The configured required units and fleet daemon are active; the router identifies the configured environment and every unlocked supervisor reports the expected commit and environment ID. Locked people do not need to be unlocked for proof. Failed runtime units reject the release; other host Pi failures remain in the proof and logs for their host owner.
- `deploy/smoke` passes for the router, open people, Voice, Meet recognition availability and web assets. Name-only protected requests fail, and each authenticated endpoint list respects its person's grants.
- No direct supervisor or development-web route bypasses the router. UID gates protect loopback supervisor and control ports.
- Each target's host-specific checks and matching Android manifest/download hashes pass. Publication records durable per-host proofs and releases each successful host reservation immediately. It reports full success only when every target has a valid delivery proof; another host's wait or failure never revokes an accepted host delivery.
