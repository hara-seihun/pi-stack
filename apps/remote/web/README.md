# Shared Remote client

The [typed UI state catalogue](src/ui-catalogue/README.md) owns synthetic rendered fixtures, actual visual review receipts and the remaining component/composition queue.

Browser and native clients authenticate at the bootstrap router before discovering endpoints. The web client owns account sign-in, person selection on key-based hosts, router sessions, and endpoint selection.

## Browser mount path

The same built frontend works at `/` or a directory such as `/pi-stack/`. [`app-path.ts`](src/app-path.ts) derives the mount from the document URL. Vite emits relative chunk and public-asset URLs. Pages, artwork, API bootstrap, downloads, Meet navigation and invitations stay under that mount. The manifest uses a relative start URL and scope. There is no Pi Remote service worker to register or a root worker to replace.

The ingress redirects `/pi-stack` to `/pi-stack/`, preserving the query string, then strips `/pi-stack` from every forwarded request. The router and supervisors continue to serve their normal root-relative routes. Do not add root API or asset aliases. There is no per-host build or browser base-path environment variable. HTML pages live directly under the mount, not at arbitrary SPA routes. See [deployment](../../../docs/deployment.md#browser-prefix-hosting).

Browser person selection, folder keys, sessions, endpoint selection, drafts, transcript caches and notification coordination are scoped by mount. Root installs retain their existing storage names. A different path starts with separate browser state and needs its own authentication. This separates deployments' state, not same-origin security authority.

Android still loads its bundled root-relative pages and uses its configured bootstrap URL, which may itself include a mount prefix. API URLs returned by the router remain relative to that bootstrap. Meet invitations use the bootstrap frontend, not the selected remote API prefix.

## Android browser download

The installed Android client owns automatic update checks at the app root, independent of the selected screen. It checks on launch, foreground/visibility return, reconnection and every minute while visible, then starts installation automatically. The entire Machine navigation button becomes **Update** while an update is pending or applying; it is the retry/reopen action, not a link to a hidden update card. Compatible web updates apply and reload directly; native APK changes still require Android's installer approval. See [in-app updates](../../kenan/README.md#in-app-updates).

Android phone browsers show a small dismissible **Get Kenan for Android** prompt, including before folder unlock. Download reads the current same-origin `/v1/app-update` manifest and navigates to `/v1/app-update/<release.fileName>` under the browser mount, retaining ingress cookies. It never uses a selected remote environment or a baked-in APK filename. Dismissal persists per browser mount. The installed app, iPhones and desktop browsers show no APK prompt; an Android APK cannot be installed on iOS.

## Private network onboarding

[`NetworkJoinPrompt`](src/network-join.tsx) reads public `GET /v1/network` through the shared fetch transport. The route always targets the bootstrap router without a folder-session header, including before unlock and while another environment is selected. Browser mount prefixes and Android ingress credentials still apply. Network status requests use the same request reporting as other API reads.

## Account sign-in

An OAuth-enabled router advertises `environment.authentication` in the public chooser as `{ type: "oidc", loginPath: "/v1/auth/login", label: "Sign in with Google" }`, with an empty person list. The client retains this host setting when authenticated environment responses omit it. The chooser request omits folder-session headers and person hints, but retains same-origin browser cookies so ingress sign-in remains effective.

Before using a saved session or asking for a key, browser bootstrap calls `GET /v1/auth/session` directly through `browserFetch` with `credentials: "same-origin"`. A successful `{ ok: true, user, session }` response replaces the selected person and enters the existing router-session and endpoint-discovery flow. A 423 opens account sign-in; a 404 means key-based authentication only when the public chooser did not advertise OAuth. Network errors, malformed sessions and unexpected statuses stay visible and can be retried. OAuth hosts never try saved keys or empty-key unlocks.

The main app and standalone Voice share the account sign-in dialog. Its button navigates the whole page to the bootstrap mount plus `/v1/auth/login`. The callback sets an HttpOnly cookie and returns to the app; no token passes through the callback URL. A lost router session attempts cookie restoration again. API headers and authenticated download URLs keep the existing router-session protocol.

On these hosts the environment picker contains only authorized environments. The client also rejects direct person changes, including stale person choices saved by a key-based deployment. Android key-based hosts keep their existing unlock flow without a browser-cookie probe.

## Native bridge

`KenanRemote.getState()` returns `{ routerUrl: string, accessToken?: string }`. The shell selects reachable private ingress or its configured public ingress and, for the latter, owns Cloudflare Access email-code sign-in. The client keeps the Access token only in memory, scopes `cf-access-token` to that bootstrap's API paths, and renews a rejected token through native validation/sign-in before replay. Background transports share the shell's selected ingress and credential. This does not replace folder authentication or permitted-environment discovery. See [Kenan sign-in](../../kenan/README.md#email-sign-in-outside-the-private-network). There is no native environment selection, preparation, or SSH setup.

`syncSession({ user, session })` replaces the native notification monitor's authorization. `session` is the opaque router token. Clearing auth sends `{ user: "", session: "" }` and stops monitoring. The monitor discovers allowed endpoints at bootstrap using this session. Every poll carries `x-pi-remote-session`; `x-pi-remote-user` is only a hint. A 423 response stops monitoring until the web client supplies renewed authorization. `notifications({ request })` checks or requests notification permission.

The haptic, keepAwake, notificationTarget, notificationThread, checkAppUpdate and installAppUpdate methods retain their existing roles; `webReady` tells the shell that a downloaded web bundle booted. Notification targets contain person, endpoint ID and thread ID, never a credential.

## Router contract

Unauthenticated bootstrap `GET /v1/environment` supplies the person chooser. `fetchPersonChooser()` explicitly uses that route without a session, even while signed in. Ordinary authenticated environment requests use the selected endpoint. `POST /v1/unlock` sends `x-pi-remote-user` and `{ key }`; success supplies `{ ok: true, user, session }`. Persons without encrypted folders submit `{}` to mint a session. `GET /v1/environments` requires that session and supplies the authorized endpoint list. Endpoint `baseUrl` values are same-origin prefixes, with an empty prefix for local. Icons are asset names from `public/`, such as `house` and `cloud`.

Unlock, lock, lock-status and endpoint discovery always use bootstrap, regardless of the selected endpoint. API calls carry `x-pi-remote-session`. Download URLs may carry `session` only on router API URLs, never external links. Keys are stored under the selected person; router sessions live in tab storage. Changing person clears session and endpoint state. A lock or router restart requires reauthentication, using the stored folder key when available. Endpoint selection checks `health.environmentId` before committing the selection; a misrouted upstream reports an error rather than opening the wrong host.

API fetches reject redirects so custom session headers cannot follow a router response to an external origin. Meet invitations contain no router session; the router does not authorize a guest by accepting the host's person name.

## Environment and person picker

[`EnvironmentControl`](src/EnvironmentControl.tsx) renders one full-width dropdown in the Machine screen containing the current person's authorized environments and every other person from the bootstrap chooser. It has an accessible name but no visible label, icon, or separate person button. People load independently of authenticated environment discovery and remain selectable during environment failures or switching. Choosing an environment uses `KenanRemote.select` to verify its identity before reloading; choosing a person uses `PiRemotePerson.set` to clear the previous session and endpoint selection, leaving authentication to the existing unlock flow. Auth and person events refresh the environment list and invalidate stale results. Each error can be dismissed through the shared [`DismissibleError`](src/dismissible-error.tsx) without clearing the failure or removing the dropdown's Reconnect option. Reconnect retries discovery and shows any renewed failure.

## Dismissible errors

[`DismissibleError`](src/dismissible-error.tsx) imports its own [CSS](src/dismissible-error.css). Pass `message` as a string, or an empty/null/undefined value to remove feedback. Optional props are `dismissLabel`, `className`, `role`, `resetKey` for a new attempt with the same message, and `onDismiss` for server-owned errors. The default role is `alert`; background feedback uses `status`.

Server-owned errors carry an occurrence ID. The client posts it to `POST /v1/errors/:errorId/dismiss` and hides the message after the server acknowledges it. While saving, the button is disabled and Dismissing is visible. A failed save keeps the original error visible with a retryable dismissal error. Server synchronization removes dismissed errors from every client, including inbox and thread summaries. Browser reloads and supervisor restarts retain dismissal.

The supervisor's `error_feedback` table owns acknowledgements. Repeated reports of the same unresolved error keep their ID; recovery and changed messages create a new occurrence. A stale dismissal cannot acknowledge a newer occurrence or an error from another thread. Dismissal does not change execution state, retry policy, native history or work outcomes.

Client-only errors, such as upload and connection failures, still dismiss locally. Keep failure state and retry actions in the caller. Changed messages, changed reset keys, or clearing the message reset local dismissal. The dismiss button has a 44px touch target and a visible keyboard focus outline.

## Slow request diagnostics

[`in-flight.ts`](src/in-flight.ts) tracks page-level progress separately from request timings, so slow nested/background API reads remain diagnosable without keeping the bar active. After 1 second, the client reports a pending timing to `POST /v1/diagnostics/requests`; when that request settles, it reports the final duration. Each report has an ephemeral page UUID, Android/browser platform, request ID, method, queryless path, epoch start time and elapsed milliseconds. It includes no body, header, message or credential. Stream, haptic and diagnostic requests stay in the background; the diagnostic POST uses the normal authenticated `window.fetch` transport and cannot keep the bar active or trigger another report. Network failures do not retry or change the original request. `inFlight.timings()` retains the latest 100 local timing records for inspection, including reports the server could not receive. The server's authenticated `GET /v1/diagnostics/requests` returns recent reports for the current person. Use the request ID and path there to identify the next slow operation rather than guessing from the bar.

## Toasts

[`toasts.tsx`](src/toasts.tsx) exports `toast` for short app-wide notices and `ToastViewport`, mounted once in the authenticated shell. [`toasts.css`](src/toasts.css) owns their styling. Sonner dismisses a toast after 3 seconds by default, pauses its timer during interaction, and lets people dismiss it with the close button or a left/right swipe. Changing account or environment clears visible toasts. Long notice content scrolls within a viewport-bound panel while action and dismissal controls stay available. Toast dismissal never changes the operation or its recovery state.

Import `toast` from `./toasts` in a client component or module. Use `toast("Saved")` or `toast.error("Upload failed")`. Pass an `id` to update an existing notice; `toast.dismiss(id)` removes it.

## Presentation

Each visible fact has one owner in the current view. Navigation pairs its icons with short visible destination labels and accessible names; provider and model icons carry accessible names and hover titles rather than repeated adjacent labels. Text-only controls remain where an icon would be ambiguous. Status uses coloured text, not a second status dot. A meter may pair its shape with one exact number; descriptions do not repeat that number.

Collapsed entries summarize their content. Opening an entry replaces its excerpt with the complete data rather than displaying both. Tool arguments, results, copy actions and original model context remain available. The inspector opens as a right sidebar, and the new-chat menu stays within the inbox column. Other modal sheets cover the underlying screen. Keyboard interaction, accessible names and distinct actions such as cancellation versus attachment remain separate from visual repetition.

### Messaging design sources

The layout adopts iMessage's [quiet timestamp disclosure](https://support.apple.com/guide/iphone/send-and-reply-to-messages-iph82fb73ba3/ios), Signal's [sent-bubble color and system themes](https://support.signal.org/hc/en-us/articles/360007320951-Chat-Colors-Wallpaper-and-Themes) and [message details on demand](https://support.signal.org/hc/en-us/articles/360054649071-View-Message-Details), WhatsApp's [rounded, aligned bubbles without decorative tails](https://9to5google.com/2026/03/09/whatsapp-embraces-rounded-chat-bubbles/), and Telegram's [message-corner grouping vocabulary](https://github.com/telegramdesktop/tdesktop/issues/25265). [MUI's Material message-list pattern](https://mui.com/x/react-chat/material/message-list) supplies the five-minute grouping window and date-divider structure; Google's [Reply study](https://m2.material.io/design/material-studies/reply.html) prioritizes functional clarity and legibility, not a chat-specific mandate. [NN/g's chat guidance](https://www.nngroup.com/articles/ai-chatbots-design-guidelines/) supports in-place progressive disclosure and leaving a reader's scroll position alone; existing scroll ownership is retained. Apple's [notification HIG](https://developer.apple.com/design/human-interface-guidelines/notifications) calls for timely, high-value information rather than redundant alerts. Machine traffic is retained inside collapsed Work, not a person bubble or an extra system-feed line.

## Canonical conversation state

Transcript `sourceKey` identifies a native message block or a tool-call identity. Body hashes address immutable content, not messages: two identical messages remain two messages. Page overlap, stream replay and live-tool finalization reconcile through this key; generation replacement discards the former branch. Native scroll anchoring and bounded earlier-page loading retain their existing owners.

Live assistant output carries its originating `messageTimestamp`. The conversation joins it against finalized assistant heads before rendering, so history arriving before the live-clear frame cannot display the same answer twice. Owner and native projections clear finished assistant output; reconnect never restores finalized text as live work.

The header reads canonical owner lifecycle and separately reports connection syncing/disconnection. A disconnected view labels execution as last known. The queue remains accessible in mono and classic. Canonical managers always retain a Send composer during execution or dependency waits; ordinary worker cancellation controls are unchanged. Manager questions remain answerable without removing its message input. On phone widths their independently scrollable composer is capped at35dvh, leaving the conversation visible. The contact name has reserved space; the compact header omits elapsed time on phones, retaining the state, queue and full details in the inspector.

Exact native `thread_landed` receipts associate submitted user bubbles with input IDs. Bounded owner metadata distinguishes queued, dispatch acceptance unconfirmed, accepted in the runtime queue, consumed/in-progress, and explicit successful/failed/cancelled turn outcomes. Historical pages carry their own input receipt; recent session receipts update live bubbles. A finished turn is not a claim that a larger task is complete. Failures show their actual reason. Prompt admission receipts preserve requested delivery identity and expose normalized `effectiveDelivery` separately.

Manager conversations keep normal chronological flow with human bubbles aligned right and Kenan replies aligned left. Input receipts remain attached to their user bubble; ordinary worker layouts are unchanged.

Managers with owner-reported all-context selection show a read-only expandable list of every selected destination file. Ordinary new-thread context selection remains manual.

## Optimistic actions

A pending mutation retains the same layout and controls with its local submission marker. Durable prompt outbox state owns saved/unconfirmed/rejected submissions until canonical admission; it does not create a second optimistic transcript message or manufacture an execution outcome. Errors belong to the affected operation and can expose recovery actions after failure or an uncertain outcome.

AI prompts use a [bounded durable outbox](../docs/prompt-outbox.md): intent is saved before HTTP, retries reuse the exact requestId/body, and accepted admission is distinct from execution. Active new-agent creation and prompt submission survive short controller replacement through [`controller-replacement.ts`](src/controller-replacement.ts), inside the shared and pinned transports: connection/body loss or HTTP 502/503/504 retries the exact request for at most 60 seconds. The selected person, session and environment remain pinned; changed ownership, cancellation and owner validation/authentication decisions stop replay. Acceptance is returned only from the owner's committed receipt. Uncertain sends survive reload with explicit Retry; rejected sends remain visible until dismissed. Stop and commands never enter prompt replay storage. Run `bun test apps/remote/web/controller-replacement.test.ts apps/remote/web/router-client.test.ts` for durable owner restart, lost acknowledgements, request identity and privacy boundaries.

## Chats and conversation

[`chats.ts`](src/chats.ts) gives AI threads and shared human rooms distinct `ai:` and `room:` identities in one inbox. Rooms use the same searchable rows, status sections, close/Undo controls, conversation header, message view and composer; they are not a separate inbox section. Their directory carries per-person visibility/unread state and owner-reported room execution activity. Status retrieval failure is visible rather than presented as cached healthy progress. The stream reconciles the AI session directory; the room directory carries the current person's shared rooms. A remote close clears the selected chat, while incoming messages never select a chat. Archived threads are not in client state: the picker loads `GET /v1/sessions/archived` when it opens, and a thread opened from the picker or a notification is held as `discovered` until the directory carries it.

[`Inbox`](src/features/chats/Inbox.tsx) groups chats as Needs you, Active and Quiet. It sorts AI threads by `attentionRank` from [`thread-status.ts`](src/features/status/thread-status.ts), then by most recent accepted user message (or creation time before the first user message). Agent replies, tool activity, notifications and thread edits do not advance that recency. The displayed time still describes the latest update. Foreground placement controls Chats, not backend custody or launch provenance. The inspector lists directly launched agents without a worker hierarchy. Launched-agent activity never changes the launcher's status or busy icon. Search filters the inbox. Its archived-search action opens the picker with the query. There is no client or server ordering API.

### Execution status is evidence, not reassurance

The shared [`thread-status.ts`](src/features/status/thread-status.ts) vocabulary is used by the inbox, conversation header, inspector and meeting view. `running` is an execution lifecycle flag, not proof of progress. Every running execution has an owned phase: Queued for execution, Acquiring model account, Preparing agent, a named preparation boundary, Reconnecting to agent, Saving execution result or Cancelling execution. These come from the code that owns each pending operation, not inference from transcript text. The runtime emits request-start evidence before an outbound model request so Waiting for model includes the first-token wait and each continuation after tools. Observed phases distinguish Thinking, Writing response, Preparing tool call, named executing tools, Compacting context, Retrying model request and Waiting for model (only when an explicit request-start event establishes that wait). Owner-recorded admission refusals display Waiting for capacity; transient provider or startup backoff displays Waiting to retry. An inactive or stopped launcher with no unresolved wait or result subscription displays **Idle**, regardless of agents it launched. Each agent retains its own status; launch provenance never changes its icon. The owner projects typed waits and unresolved result subscriptions into one **Waiting** state. Remote normalizes that activity once in [`projectThreadActivity`](../server/live-projection.ts), shared by all clients; clients never infer peer liveness from IDs. Active execution takes precedence. Native `thread_await` also reports Waiting from its observed tool phase. Wait reasons remain visible, with their own start when recorded and no stale-model silence warning. The [self-wake contract](../../../docs/threads.md#durable-dependency-waits-and-own-thread-wakes) owns resumption and timing: Thread inspector displays reason, interval, next requested due, last due/queue/landing and stopped/archived/busy deferral. Neither a wait nor a timer can override Stop or archive. Owner-recorded execution errors display Execution error, with the reason visible in the conversation and inspector, rather than Idle. Pending cancellation displays Cancelling; confirmed cancellation returns to Idle or Archived; a recorded cancellation error displays Cancellation failed. There is no persistent Stopped state.

`activitySince` dates the observed phase; `lastActivityAt` dates its latest execution activity. Status pills show the elapsed phase time and, after 15 seconds without an activity update, the time since that update as a bare duration visibly, including on phones and dense rows. This is not a failure verdict: a silent Bash command can be healthy, and a reconnect observation does not prove progress. Missing timestamps stay missing. The inspector exposes phase evidence and both times. Reading/reconnecting never refreshes these progress clocks; settlement and Stop remove execution clocks from the display. Missing phase or active-tool identity is a **Status reporting error**, an actionable instrumentation defect, not a supported normal execution state. All controlled boundaries must report their actual owned phase; adding an unknown/busy catch-all instead of instrumenting the boundary is not an acceptable implementation. UI states must name machine state and the operation being awaited, never disguise it as generic work. Dispatch is exhaustive over closed types, with no switch default. Unknown or missing discriminants are rejected at stream, route and native-update boundaries with explicit errors. An idle lifecycle reporting an execution phase is a status-reporting defect, never Idle. Legacy wait metadata without a dependency kind remains preserved and visible as **Wait type missing**, never coerced to an agent dependency.

[`MessageReactions`](src/message-reactions.tsx) renders under each stable message. Only messages with a server-issued `identity` get controls; live answers and pending sends have none. A chip lists the people who used that emoji. React in the message menu opens common emoji choices, the person's existing reactions and an input for another emoji. Selecting an owned reaction removes it. Escape returns focus to the message; tapping outside closes the picker. The server marks the current person's reactions with `own`. The client sends `{ messageId: identity.id, emoji, remove? }` to `POST /v1/messages/reactions` and replaces the chips with the returned reaction list. Failed requests leave the existing chips intact and show a dismissible error beside them. The long-press menu, drawing and copy actions remain on the message itself.

[`thread-discovery.ts`](src/thread-discovery.ts) resolves transcript reference names across inbox, fleet and discovered rows. Known rows need no fetch; duplicate requests coalesce and historical references use at most four concurrent lookups. Name-lookup failures stay on the reference tooltip, never create global toasts or mark the conversation missing. Subsequent discovery can retry a failed lookup after 30 seconds; opening a reference is a separate explicit action with its own visible error. Responses must identify the requested thread. Auth/person unmount disposes its discovery owner: queued lookups are dropped and late responses cannot update the next lifetime; StrictMode setup lazily creates a fresh owner.

Agent-to-agent message disclosure headers keep the selected agent on the left in green and the peer on the right in blue. Incoming messages show recipient ← sender; outgoing messages show sender → recipient. The shared [`AgentRoute`](src/features/conversation/agent-message.tsx) controls every header. Incoming messages retain the sender's `agentName`, with a link to its original thread. Historical envelopes are parsed without rewriting native history. Task titles remain separate from names, and the selected agent's own assistant replies are labelled Kenan. Quoted examples and human messages are not reclassified.

The inspector's Settings → Display section offers **Auto-collapse work and thoughts**, enabled by default. The saved preference applies to all chats for the selected person on this device, scoped by browser mount. Turning it off renders every thought, tool call, system prompt and tool schema as an initially expanded individual step, with no work-card grouping. Live thinking subscribes automatically while the selected conversation is visible, and completed steps stay open when subsequent steps or the final answer arrive. Individual steps can still be closed manually.

With auto-collapse enabled, a conversation transcript keeps every user and assistant message and puts each intervening stretch of agent work in one work card. The collapsed card summarizes its steps and shows the latest one. Expanding a card shows every entry in order: tool calls, thinking, system prompt and tool schemas. Tool arguments and result blocks appear once, preserving their original content and order. Arguments and the complete result each scroll inside a keyboard-focusable panel capped at 14.4rem or 30% of the viewport height, whichever is smaller. At either edge, scrolling continues into the conversation. Multiple result blocks share one scroll area; streaming output uses the same bound. Copy still retrieves the full call, not just the visible portion. Expanded text steps replace their opening preview with the body. The header owns thread status and queue access; the current step owns the active tool name. The composer provides Cancel work or Send, with a delivery menu for queue, steer or hard steer. Launched-agent activity alone does not change Send to Cancel: local execution, an explicit wait or a wake schedule does. Cancellation targets only the selected agent, discards cancelled pending work and does not archive it. The header's Cancel action uses the same behavior. Delivery defaults to steer when opening a thread or changing its running state; an explicit choice lasts until then. That menu lists alternatives to the current mode. Pending questions replace the message composer until answered or dismissed. Their resource has loading/ready/failed states with explicitly stale questions, resource-only Retry, and no chat-offline side effect.

The AI chat header shows an estimated current-context token count alongside its model, compactly (for example `~12.3K tok`). [`ContextTokens`](src/features/conversation/ContextTokens.tsx) consumes the optional session `contextUsage` supplied by native Pi usage, anchored to provider usage, not the visible transcript size or cumulative billing tokens. Its tooltip and screen-reader text give the unshortened estimated count, model context window and usage percentage when available. Absent usage shows `Context —` (unavailable); null tokens after compaction show `Context …` (recalculating until the next model response), never a fabricated zero. On narrow headers, status gets its own line and the model truncates independently of the count.

On desktop, a visible selected list row owns the thread title while the conversation header owns model and status. Filtering, collapsing or scrolling that row out of view restores the title to the conversation. Phone detail always shows its title. The information button is the sole inspector action.

Neither the Markdown renderer nor KaTeX is in the page at startup, and the inbox, Attention, Files and Machine screens need neither. [`markdown-engine.ts`](src/markdown-engine.ts) downloads markdown-it, texmath and the delimiter shim when the first `Markdown` component mounts; until they arrive a block shows its own source as escaped `.markdown-plain` text with its line breaks. [`math-engine.ts`](src/math-engine.ts) downloads KaTeX, its stylesheet and fonts when the first formula renders; until then formulas show as `.math-pending` monospace source. Either arrival re-renders every mounted Markdown block. Compiled formulas are remembered, so a streaming message does not recompile them on every chunk. A test with the vendor scripts already on `window` gets the renderer synchronously; anything asynchronous awaits `ensureMarkdown()`.

The paintbrush opens white paper. Clicking an image, or focusing it and pressing Enter or Space, opens that image in the same editor for either kind of chat. Image attachments show the preview without a second filename/download link beneath it. The image editor has a Download action for the original file; non-image attachments keep their links. Opening an image copies its decoded preview to a draft-owned bitmap, without retaining the transcript's DOM node. Pointer frames copy a viewport-sized backing canvas and paint the active stroke, rather than resampling the original image and repainting every completed stroke each time. Pan, zoom, resize, undo and stroke completion rebuild that backing canvas. Inactive drafts release both viewport pixel buffers but preserve strokes; removing a draft closes its bitmap. Owned context image downloads request server attachment disposition, so Download also works from Android's cross-origin client. Each chat and source image keeps its own drawing draft. Cancel retains the draft; Attach uploads a PNG to the originating chat's attachments without sending it. Attach is disabled until a new drawing has a stroke; an existing background image can be attached unchanged. Send submits the attachment even without text. An upload failure keeps the editor and strokes available for retry; a successful retry clears the error. Both kinds of chat hide their composer and conversation header while drawing, then restore focus to the control that opened the editor.

## The stream

[`stream.ts`](src/stream.ts) owns a bounded retained replica, not a connection session. Opening, selecting, refreshing, returning to the foreground or changing network sends finite `POST /v1/reconcile` with wanted resources and the revisions actually held. It returns `{events}` with bootstrap, reconciliation frames, ordered notification pages and the selected thread's inspected readiness acknowledgement. No previous stream ID or server-held client state is required. Only after applying that result does the client attach disposable `POST /v1/stream` push using its new revisions. Healthy push needs no reconciliation polling. If push fails, finite synchronization recovers immediately; repeated failures back off to five seconds. A generation fences both transports, including late responses after abort. Subscription changes replace the generation rather than queue behind a stream update.

Resource IDs include `bootstrap`, `state`, `dashboard`, `workers`, and session-qualified `transcript`, `live`, `images` and `questions`. Generic frames apply before complete typed snapshots reach the app. Missing patch bases discard that resource's claimed revision and request its complete value. Complete state removes rows deleted while disconnected. Normal app feeds cancel connections, requests and timers while hidden; Voice/Meet opt into intentional background transport. Native notification ownership takes over with its durable cursor and replay lease. Cached content remains readable during recovery; only acknowledged state is presented as current.

Live answer and thinking text never enter the app's state. [`live-text.ts`](src/features/conversation/live-text.ts) is a small store the open conversation subscribes to, so the server's 33 ms frames re-render that conversation and nothing else: not the inbox, the inspector or the tab badges. `Inbox` and its rows are memoized for the same reason.

Finite synchronization and push opening each have a five-second deadline; a push body with no bytes for thirty seconds is discarded. `online`, native `pi-network-changed`, `pageshow`, `focus` and visibility return reconcile immediately even if the old socket still claims to be open. Simultaneous wake events coalesce. The first failed attempt retries immediately, with bounded backoff only after repeated failure. Successful finite reconciliation does not depend on push availability. The [error attention contract](../docs/errors.md) applies at this recovery owner: ordinary revalidation, subscription changes, disposable push replacement and missing-patch-base repair preserve healthy connection status. Selection readiness independently reports Updating until acknowledged. Only a failed finite synchronization starts the five-second connection-loss grace; an uninterrupted outage then shows **Connection lost. Reconnecting…**, including between retry attempts. Raw transport details remain in `StreamStatus.diagnostic` instead of the attention message. HTTP 401/403/423 require sign-in/unlock immediately; the normal `piFetch` path opens the unlock UI on 423. HTTP success alone cannot clear an outage: the whole finite response must validate and apply first. Non-viewing clients require hello; a visible conversation requires its current selection acknowledgement and applied revisions. That acknowledgement also clears a recovered protocol refresh error, without clearing a concurrent connection failure. Connection state drives the conversation status and Reconnect action. Frames scoped to a session the person has left are dropped before the app sees them.

The subscription follows the route: the open thread, whether it is visible, the Machine screen only while it is showing, and live thinking while the thinking card is open or auto-collapse is disabled for a visible conversation. `state` carries foreground, selected, working and recent agents, plus useful launch provenance, independently of backend custody. Open agent and Agents read the complete live `allAgents=1` directory. Agents alone subscribes to fleet status while visible; its complete directory retains quiet rows excluded from the recent stream projection. The fleet keeps thousands of settled threads, and carrying them made every reconnection download and hash about 2 MB before a chat could leave Updating. Reopening a thread paints a resident snapshot before reconciliation completes. Its header immediately shows an Updating spinner instead of the cached execution status, while the transcript stays readable. Each reconciliation generation has a fresh `selectionId`, retained when attaching push. The supervisor sends `selection-ready` after inspecting the selected owner and publishing its transcript, live text and state, even when those resources are unchanged. That opening rebuilds the inbox once, at acknowledgement, rather than both before and after inspection. Inbox projection excludes archived fleet rows before deriving their placement and reuses the local snapshot for origins; shared archived ancestors are read once per projection. Fleet refresh initializes views only for newly discovered threads and updates model recency only for changed revisions. The client clears Updating only when that acknowledgement matches the current opening and all three applied resource revisions. Cached replays, hello, inbox updates and stale acknowledgements cannot finish a refresh; thinking and cursor changes cannot abandon one. A failed refresh keeps its error and Reconnect visible until a matching successful refresh, instead of falsely claiming current state. `notificationsAfter` carries the current environment's idle cursor, so its settlements ride this connection; other granted environments keep a 30-second poll of `GET /v1/notifications`. Voice opens its own stream with `{session, eventsAfter, viewing: false}` and consumes durable `events` and reconciled `live` snapshots.

## Transcript items

The supervisor derives ordered items from the model context: system prompt, tool schemas, user and assistant text, thinking blocks, and each tool call with its result. The app requests the newest 60 heads on the stream, never the entire loaded-to-live suffix. [`transcript-store.ts`](src/features/conversation/transcript-store.ts) retains a paged window of at most 600 heads and 8 MiB. While following the tail, it continuously evicts older heads; while reading, a visible sequence range protects the anchor. An update that would evict that range freezes the held page and exposes Show newer and Jump to latest instead. Show earlier/newer each loads 60 heads and evicts the opposite edge; Jump to latest replaces the page with the newest 60. A new generation from compaction, a fork or tree navigation replaces the window. One individually oversized head, or corrected content of an already displayed protected page, remains readable rather than silently disappearing.

Paging uses `GET /v1/sessions/:id/transcript`; a 409 carries the generation that replaced the one asked for, along with its newest window. The stream continues delivering only the recent tail, while older pages are fetched explicitly. An empty native generation with no items means the thread has no finalized conversation history yet. A cold selection whose transcript has not arrived instead shows Opening conversation; failed refresh shows Conversation unavailable and Reconnect. Neither pending nor failed history is rendered as a completed context/work event. Retained acknowledged history remains readable during recovery.

[`VirtualTranscript`](src/features/conversation/VirtualTranscript.tsx) continuously bounds each transcript/work-step/message list to 60 mounted rows, using measured spacers to retain scroll access. It measures rectangles rather than assuming positive scroll offsets: conversation scrollers use reverse flex. Expanded work cards virtualize their steps too. Stable history grouping and summaries are memoized separately from live thinking; text changes reuse settled rows and the trailing work array. Status and work/tool clocks share one timer and one intersection observer, and only visible foreground subscribers tick.

Canonical context images inside item text arrive as `/v1/sessions/:id/images/:hash` Markdown images; the renderer resolves those through the selected endpoint and router session, as tool-result image blocks are.

The newest item of a window carries its complete `body` inline when it is under 8 KB: that is the step a person opens first, so it renders whole without a request. [`ItemBodies.accept`](src/features/conversation/item-bodies.ts) takes those bodies as the window changes and writes them to the same cache the fetched ones use. Heads carry only what names a step — strings cut at 120 characters, arrays at five entries, an edit's `editCount` instead of its edits, no written file content and no delegated message — so [`tool-summary.ts`](src/features/conversation/tool-summary.ts) reads `editCount ?? edits.length` and shows the diff only once a body has arrived.

Returning to a thread paints its cached heads, loaded bodies and inline-image metadata synchronously, before any disk or network request. [`client-cache.ts`](src/client-cache.ts) owns this memory across all AI threads in the authenticated app. Thread snapshots retain the newest 200 heads, with a 32-thread, 8 MiB limit and a 30-minute idle lifetime. Immutable bodies have a separate 2,000-entry, 32 MiB budget. Both use access-ordered eviction from [`resource-cache.ts`](../shared/resource-cache.ts). Open mounted steps take explicit body leases from that same owner, so eviction cannot erase displayed text or tool results; closing or virtualizing away the step releases its independent reference. There is no selected-thread body map outside the budget. Obsolete inline tool/thought bodies are stripped from retained older heads after delivery. Concurrent body requests share one promise even when navigation remounts the conversation, and locking fences late results from repopulating the next cache lifetime. Locking or changing person discards the memory owner; environment switching reloads it. Persistent keys include person and environment.

The same owner caches content-addressed transcript images through [`cached-media.tsx`](src/cached-media.tsx). Concurrent consumers share one fetch, and returning to a screen reads its retained blob URL synchronously instead of restarting a loading placeholder. Media has a 512-entry, 32 MiB memory budget and a 512-entry, 64 MiB bucket in the shared IndexedDB database. Mounted consumers hold leases so eviction does not revoke a picture still in use; the last lease releases an evicted URL, and locking disposes all URLs and cancels in-flight fetches. Disk keys omit session credentials and include the owner's person/environment scope. New content hashes select new entries. Mutable file previews, arbitrary external images and streaming audio/video remain on their normal transport rather than being frozen into this immutable-media cache. Drawing and downloads retain the original authenticated source URL alongside the cached display URL.

Question refreshes keep their last settled state, including an empty list, while the owner reads the next snapshot. Unchanged questions therefore emit no new reconciliation frame; routine thread activity never resets them to loading. Healthy question reads add no loading banner above the composer. A failed read preserves the previous questions and exposes its own error and retry action without marking the chat offline. Finite selection synchronization awaits the question result before closing its response, so a slow owner cannot leave the client permanently loading.

The stream refreshes cached threads when selected. Memory and disk windows seed the replica with the hash of their exact held JSON, so a reload declares a real revision instead of discarding cached heads. An empty window or changed generation is authoritative. Archiving, remote removal and forking drop the cached thread. Cold openings use IndexedDB without allowing a late disk response to overwrite a newer stream frame. Pointerdown, unread arrival and selection never fetch a duplicate transcript window. Each thread batches its own disk writes, so switching threads cannot cancel another thread's pending save.

Long message previews offer a small centred **Load more** action in a footer below the text. The footer reserves a separate right-hand column for Copy, so expansion, loading and retry labels never inherit the copy icon's fixed width or overlap it. Ordinary, incoming-agent and outgoing-agent messages share this layout; expansion and copy still retrieve the exact native body.

Bodies load on demand from `GET /v1/sessions/:id/items/:itemId`, addressed by content hash, when a step opens or a copy button needs the complete text. [`transcript-cache.ts`](src/transcript-cache.ts) keeps them in IndexedDB, never invalidated, bounded to 2,000 entries and 64 MiB with least-recently-used eviction. Disk windows retain at most 32 threads and 8 MiB. A metadata store tracks counts, bytes and access order, so writing one body no longer reads every cached payload, and reading one no longer rewrites it. Oversized entries stay out of the cache. The database upgrade builds metadata once for existing entries. Expanding a step still shows the exact model context, with nothing added or omitted: only delivery is lazy. A collapsed row shows the head's preview, and a step waiting for its body says so.

Live answers and thinking arrive as reconciled full text snapshots. Thinking streams only while the person has the card open: opening it subscribes, closing it or leaving the thread unsubscribes, and nothing about that choice is stored.

## Shell, inspector and machine

[`Shell`](src/app/Shell.tsx) has five hash-routed destinations: `#/chats`, `#/attention`, `#/agents`, `#/files` and `#/machine`. `#/needs-you`, `#/notifications` and `#/calendar` resolve to [Attention](../docs/attention.md). Old `#/workers/:id` links open the original agent under Chats and human opening promotes it without replaying cancelled work. Attention interleaves personal deadlines and [calendar](../docs/calendar.md) events while retaining event editing, month selection, display zone and ICS Sync controls. Below 900px it shows one pane and a bottom tab bar. Detail screens have Back, and each navigation pushes browser history. At 900px and above it shows an icon rail, list pane and detail pane. [`Sheet`](src/app/Sheet.tsx) supports a modal view and a nonmodal right sidebar. The inspector uses the sidebar on desktop and phone, leaving part of the conversation visible. Queue uses the modal view. Phone inspector and queue routes end in `/inspector` and `/queue`, so Back closes them. [`system-back.ts`](src/app/system-back.ts) answers the Android shell's back gesture with the same order the back arrow uses and returns false when nothing is left to close.

[`InspectorSheet`](src/features/inspector/InspectorSheet.tsx) has Thread, Settings and Timeline tabs. Thread shows separate agent name/task title, placement, explicit dependency links, launch provenance, a direct Agents launched list including archived agents, and Debug, which contains Voice and Meet controls. Settings uses [`SettingsFields`](src/thread-settings.tsx). Timeline loads `GET /v1/sessions/:id/events`. Model, thinking, speed and bash-timeout controls remain available while a thread runs or holds queued messages. Model changes select the next execution without interrupting current work. Archived threads must be restored before editing.

Changing a setting selects its expected value immediately, with a small Saving label until the response arrives. A model change also updates its thinking and speed choices. A failed save restores the last server snapshot and reloads settings to reconcile a partially applied or unacknowledged write. Request identities prevent earlier loads from overwriting a pending selection.

The selected option uses the server's saved model identity, not a pooled account alias from a running provider request. Each thread mounts its own inspector state, so a late save response cannot replace another thread's settings. The open inspector refreshes when the thread revision changes. Failed settings and child-list loads retain a Retry button even after dismissing the error; a failed save leaves the controls available.

Machine uses one provider mark per plan card, one remaining value with pace, a quota-window description, and an optional 24-hour cache value. Coverage and unavailable readings are separate facts. Configured actions are full-row switches. The Models card in [`Models`](src/features/machine/Models.tsx) uses the dashboard's `modelAvailability` catalog, including disabled models, to show named switches with explicit Enabled/Disabled states. The dashboard's `canManageModels` enables editing only for the host administrator; absent or false means read-only disabled switches. Administrator switches send the desired `{ enabled }` state through `PUT /v1/models/:id/availability`, percent-encoding provider/model IDs. The pending row is disabled while saving; failures are dismissible and leave the server-owned state untouched. The host-global policy at `/var/lib/pi-stack/model-availability/policy.json` applies to everyone's new threads on that machine, never existing threads. Updated dashboard and bootstrap events supply the authoritative availability and start-picker choices. Android update progress appears in its action button rather than a second progress sentence.

## What loads when

The first paint is the shell, the inbox and the conversation; everything else is its own chunk, one per screen or feature, so opening one costs one request rather than six. `React.lazy` covers [`FilesScreen`](src/features/files/FilesScreen.tsx) with its authenticated editor launcher, [`MachineTab`](src/features/machine/MachineTab.tsx) with the environment picker, notification control and app updater, [`AttentionScreen`](src/attention.tsx), [`AgentsScreen`](src/features/agents/AgentsScreen.tsx), [`InspectorSheet`](src/features/inspector/InspectorSheet.tsx), [`QueueSheet`](src/features/queue/QueueSheet.tsx), [`PasteTextDialog`](src/PasteTextDialog.tsx) and the drawing editor behind [`useChatDrawing`](src/chat-drawing.tsx). The sheets and dialogs mount when they open rather than rendering closed, which is what keeps their chunks off the first paint.

The chat picker is split from its button: the inbox paints the `+` immediately through [`chat-picker-lazy.tsx`](src/chat-picker-lazy.tsx). Both the initial button and the loaded picker import [`chat-picker-trigger.css`](src/chat-picker-trigger.css), so its size and accent styling do not wait for the first tap. Activating it loads [`ChatPicker`](src/thread-start-menu.tsx), including archived search and thread/room creation. Inbox archive search uses its typed `open` handle to select Archived and retain the query through lazy loading. Focusing the button does not open it. Voice is the same shape: [`voice-lazy.ts`](src/voice-lazy.ts) publishes `window.PiRemoteVoice` without WebRTC, and the first mic toggle loads [`voice.ts`](src/voice.ts). The Voice and Meet pages import it directly, because there voice is the reason the page exists. `DELIVERY_LABELS` lives in [`delivery.ts`](src/features/queue/delivery.ts) so the composer's delivery menu does not pull the queue sheet into the first paint.

Measure with `npm run build`: the compress step prints the largest twins, and `assets/index-*.js.br` is the app chunk. Removing the blocking vendor scripts and splitting the screens took the first paint from about 174 KB to 93 KB brotli — the app chunk, React, the shared chunk, the stylesheets and, before, 45 KB of markdown-it, texmath and the shim. The app chunk itself went from 55.8 KB to 28.6 KB.

[`AttentionScreen`](src/attention.tsx) composes [personal items](../docs/needs-you.md), durable notification history and calendar data without merging their stores. Now holds undated/due personal items, active updates/questions and already-started events; Upcoming interleaves future deadlines and events by instant; History holds resolved notifications. Linked question notifications are deduplicated, and question links select the original question composer. [`NotificationCard`](src/features/notifications/NotificationCard.tsx) opens the source thread. Sources load independently, show their own failures and retain last data. Coverage and delegation expands receipts and policy. [The wire contracts](../docs/state-machine.md#notifications) own notification history pagination and question resource states. [`FilesScreen`](src/features/files/FilesScreen.tsx) opens the person's separately authenticated [code-server editor](../../../docs/editor.md). Filesystem browsing and editing live there, not in the app. Direct-path attachment selection still uses authenticated `GET /v1/files/info?path=…`; chat artifact previews and downloads remain in [`inline-files.ts`](src/inline-files.ts). [`editor-launch.ts`](src/features/files/editor-launch.ts) carries the one-use handoff only in a POST body and closes the browser editor window on identity/session changes. [`MachineScreen`](src/features/machine/MachineScreen.tsx) shows plans, actions, host usage, environment, notifications, app updates and owner errors. [`StatusPill`](src/features/status/StatusPill.tsx) renders status as text, shared by inbox rows, conversation headers and inspector.

## Global loading indicator

The thin top bar tracks initial app readiness, selected conversation and Machine-section readiness, lazy screen chunks, and user actions. The stream closes its own section scope on the first usable result (or an error); switching sections cancels the previous scope. The shared `window.fetch` door in [`native.ts`](src/native.ts) classifies transport operations in [`in-flight.ts`](src/in-flight.ts): explicit actions and top-level user-triggered reads show progress, while stream updates and descendant transcript/item/image/audio/download fetches do not keep the global bar running. Each component keeps its own skeleton, progress and error treatment independently.
