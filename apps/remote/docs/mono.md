# The forever conversation

Each account starts in classic view. Long-press **Chats** in the desktop rail or phone tab bar to enter mono view: one full-screen conversation with the person's managing Kenan. Long-press its header to return to classic. Titles describe the gesture and the first mono opening presents a one-time hint. Preference and hint acknowledgement live server-side in the person's canonical manager-owner supervisor database. Its subscribed devices receive updates through Bootstrap. Devices viewing another authorized environment read that owner's state on opening, focus/visibility return and every thirty seconds while visible; they never store another preference. Opening a thread link from mono uses the classic conversation screen; Back returns to mono without changing the saved preference.

The existing conversation and composer provide dictation, attachments, questions, images and conversation history. Mono presents one Kenan: normal status is Idle, Working or Typing. It has no tabs, thread list, inspector, queue chips, ancestry, delivery-mode picker or orchestration indicators. Person input, question answers and assistant text remain plain message bubbles, including text before an unsettled dependency wait. Each human turn has one initially collapsed Work summary containing its thinking, tools, notices and incoming/outgoing agent messages, including activity that arrives after a visible assistant reply. Replies stay outside that group. Opening Work exposes readable step summaries, such as “Waited for 7 agents” or “Ran bash”. Each step has its own initially closed disclosure: raw arguments/results, child-thread chips, thinking detail and agent-message bodies sit behind that second level, including failed and running tools. Bounded transcript heads retain the true agent count even when their ID array is shortened. The group keeps its human-message key and expansion state when virtualization remounts it. Mono uses summary-only collapse and suppresses reply response metrics. Live thinking belongs to Work and subscribes only when its detail is opened. Classic retains its existing routed messages, latest-step previews and individually expanded chronological view. Quiet heartbeat turns remain in native history; records explicitly marked hidden, including wake input and quiet assistant replies, stay suppressed in mono.

## Manager custody

The person's canonical owner supervisor creates their one manager lazily on the first mono toggle, with no initial message or model call. Toggling from another environment routes to that same supervisor and conversation; it never creates another manager or copies context between hosts. Explicit thread links can still open another environment's classic conversation. The account-bound manager relay carries notices and question decisions across authorized environments, without importing the manager's context or history. It is an ordinary full-context thread, identified by `metadata.manager:true`, protected from explicit and automatic archival. Cancel stops current work without deleting its identity. Its initial model is `anthropic/claude-opus-5-5`, high thinking, standard speed. Its prompt is source-owned [`server/manager-prompt.md`](../server/manager-prompt.md), loaded fresh on each turn together with the destination's chosen context files.

The canonical owner's ordinary ThreadService reconcile timer owns a conditional five-minute inactivity watchdog. While canonical lifecycle reports execution, runnable input or an unresolved dependency wait anywhere in this person's granted environments, five minutes without an accepted human message schedules one quiet manager check. It repeats every five minutes until human conversation resets the clock or work becomes idle. Agent sends, tool events, automated watch spawns and future wake schedules do not reset human recency or count as active work. A manager turn consisting only of its watchdog check cannot keep the watchdog alive.

`manager_watchdog` in the canonical thread-owner database stores human recency, next due time and monotonic delivery sequence. An overdue check becomes one coalesced queue intent even while the manager is busy. Its queue-only delivery never steers an active turn; it takes the next native admission boundary ahead of agent notices, without waiting for a sampled idle gap. Per-thread serialization prevents overlapping turns and a second unfinished watchdog check. Admission refreshes the work/human summary, withdrawing a check whose work became idle while the prior turn finished. Human input and an idle transition withdraw an unadmitted check. Restart preserves the due intent and accepted work identity. Explicit manager Stop/cancel pauses conditional checks until human conversation resumes. There is no separate interval, watch model or automatic four-hour heartbeat; the previous unmodified creation heartbeat is removed during owner startup. Other explicitly authored thread wakes remain independent.

The account-bound router bridge aggregates only `{activeWork,lastHumanMessageAt}` from every granted environment, each using its local supervisor/fleet canonical lifecycle and indexed human-ingress timestamps. It transfers no thread identities, paths, context or transcripts. Missing granted owners yield an explicit watchdog error, not an invented idle observation. Only the canonical supervisor installs the watchdog; nonowners expose metadata summaries without creating a manager. The manager's prompt explains that the controller owns this timer.

The person registry supplies:

- `PI_REMOTE_MANAGER_ENVIRONMENT`: canonical manager owner environment ID. Unset means this person's sole current supervisor. Cross-environment accounts set the same owner ID in every registry. Nonowner supervisors advertise the pointer and do not instantiate manager state; the client uses its authorized environment catalog to reach the owner. An unavailable or ungranted owner is an explicit error.
- `PI_REMOTE_MANAGER_MODEL`: optional catalog name or installed provider/model, validated at supervisor startup. Unset deliberately selects `anthropic/claude-opus-5-5`; thinking is high and speed standard.
- `PI_REMOTE_MANAGER_DESTINATION`: optional offered full-context destination. Unset selects Personal when offered, otherwise Home, otherwise the first offered full-context destination. Raw and sandbox are rejected.
- Each `PI_REMOTE_THREAD_DESTINATIONS` entry may declare `managerContextFiles`, top-level Markdown names in its `contextDir`, alongside `watchContextFiles`. An omitted choice uses every top-level Markdown file in that directory; a destination with no context directory loads none. A configured choice without a full-context directory is invalid. Missing configured files reject first creation and, after creation, remain explicit context-load errors rather than selecting another file.

The supervisor's `PI_REMOTE_ROUTER_PORT` must match its local root router; the existing host initial port is 8788. No new endpoint, credential or home-context grant is needed for the relay. Every participating registry sets the same `PI_REMOTE_MANAGER_ENVIRONMENT`; its existing `remoteAccess` and per-person host-catalog upstream must grant that environment in both directions for question callbacks.

Configuration belongs in each person's registry, never source. Reload through the ordinary supervisor lifecycle to apply registry changes. The manager stays in its accepted destination and settings; subsequent view toggles do not migrate or reconfigure it.

## Questions

Questions remain in durable manager custody. The manager can list them, answer with explicit manager attribution, or forward one rewritten question covering several originals. In mono, no question opens a panel, creates a badge or notifies automatically. To present its answer composer, the manager explicitly calls `thread_attention` with that exact manager question ID or question link in its authored summary. Unrelated attention does not expose other questions. The first accepted answer settles the linked group and fans out to original threads; retries cannot send another answer.

Mono holds do not expire into human attention. Classic retains its two-hour release and direct manager questions. Custody, routing and answer receipts survive restart. See [asynchronous questions](questions.md).

## Human attention

The account preference owns delivery, including while a linked classic screen is open. In mono, only the canonical manager's explicit `thread_attention` reaches web toasts, Android alerts, notification history or unread badges. Worker/watch notices, room updates, questions and settlements go durably to the manager. Its own completions and question events stay silent. Stored classic notices are filtered without erasing their history or read receipts; switching back restores classic behavior. Android applies the same server policy to cancel stale alerts and queued toasts.

Nonowner supervisors use the root router's loopback `/v1/agent-manager` bridge. Kernel UID selects that account's registered person; its existing environment grants and upstream credential select the canonical owner. The receiver permits policy read, stable manager notice delivery, minimal question-origin identity, correlated question custody and bounded own-person work summaries. Policy returns a view bit and opaque manager ID, never thread metadata, context, paths or history. `manager-origin:THREAD_ID` metadata in the canonical supervisor records a foreign question's router-stamped environment for restart-safe answer callbacks. Missing owner/grant/transport is an explicit error, never permission to notify in classic mode.

## API and storage

At the canonical owner, `GET /v1/manager` returns `{view, managerThreadId, hintSeen}`. Another supervisor returns `409` with `code:'manager_owner'` and the owner `environmentId`. Bootstrap carries `managerOwnerEnvironmentId` and either that owner's view or explicit `manager:null`. `POST /v1/manager` accepts `{view:'classic'|'mono', hintSeen?:boolean}` from the authenticated person. Entering mono creates the manager before saving mono. A mono response always has a manager ID. Failed initialization keeps classic and retains the reserved identity for an idempotent retry.

`manager_view` in `DATA/supervisor.sqlite3` owns view, hint and creation initialization custody. The ordinary thread owner database owns the actual manager and question state. No browser-local preference, alternative transcript or new task scheduler exists.
