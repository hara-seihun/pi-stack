# Write ROCm encoder (GMKtec)

The pinned `nvidia/nemotron-speech-streaming-en-0.6b` native checkpoint (revision `ebe59e5a817142986528bbbee5dba8db7b38ed50`, SHA-256 in `gpu-model.json`) runs its cache-aware encoder at 160 ms on ROCm PyTorch 2.14.0 with Transformers 5.16.1. The small RNNT decoder/joint and cleaner remain on CPU. `deploy/write-engine` installs separate hash-locked GPU dependencies and revision-pinned weights only where `/etc/pi-stack/write-gpu` opts in. Converge installs the original INT8 ONNX CPU engine. GPU admission uses an 8 GiB host / 2 GiB GTT fixed-budget secondary resident lease; denied admission, missing weights or an unavailable ROCm device selects the CPU encoder. GMKtec's DynamicUser device and admission access are declared in `/etc/nixos/pi-write.nix`; the resident admission implementation is `/etc/nixos/gpu_job.py`.

Native FP16 model allocation after warm-up is **1,214 MiB GPU**. The service process reached ~6 GiB host memory with the checkpoint, PyTorch runtime, ONNX decoder and caches; the reservation includes headroom for growth. A 160 ms encoder step is **~33–35 ms median** in isolated matched-audio runs; profiling showed 216 small GEMMs consuming 16.7 ms GPU and 889 kernel launches, with ~25.5 ms total GPU kernels. This does **not** meet the desired <20 ms encoder-step target. Batching accumulated audio four chunks at a time keeps a lagging decoder from retranscribing each chunk separately. Warming the 16/32/48/64-mel-frame shapes before listening avoids a first-use >1 s HIP kernel setup on a dictation. Live steps have priority over speculative work, and encoder calls serialize so simultaneous tiny GEMVs do not trample one another.

Matched 10 AMI spontaneous clips (145 reference words) gave CPU INT8 **9 errors** versus GPU FP16 **10 errors** after case/punctuation normalization. Ten DisfluencySpeech audio clips (183 raw-reference words, including transcript annotation tokens) gave CPU **21** versus GPU **22** errors. The native model and CPU ONNX export can differ by a word at short utterance starts, but neither corpus shows a broad WER regression. Scripts/results: `/home/kenan/work/pi-stack-write/asr/compare_native.py`, `gpu-probe/ami-matched-{1,2}.jsonl`, `gpu-probe/ami-frontend.jsonl`, `gpu-probe/public-{0-4,5-9}.jsonl`, and `native-trace.json`.

Real 16 kHz Opus paced through the Remote supervisor (`probe_e2e.py` and `gpu_probe_pairs.py`) gave one two-concurrent ten-finish series **p50 0.02 / p95 84.83 ms server flush**, with speculative hits ~0.01 ms. Another ten-finish run gave **p95 136.42 ms**, and six finishes beside four short single-thread CPU workers gave **p95 147.72 ms**. Receipts: `gpu-probe/pairs-10-serialized.jsonl`, `pairs-10-high-priority.jsonl`, `pairs-6-cpu-load.jsonl`. The hard 100 ms worst-case final is **not achievable under arbitrary co-tenant GPU or CPU load**. Live steps have a high-priority HIP stream, but that cannot preempt a peer's already-running kernel. A second two-thread ORT CPU recognizer keeps an independent cache and incremental cleaner beside the GPU recognizer when GPU busy is ≥75% or a preceding step was slow. Immediate finish races both fully decoded finals and returns the first; when the GPU is idle, the CPU shadow stays dormant to avoid taxing the GPU path. A transient GPU admission denial uses CPU and retries admission every 20 seconds for future dictations. Failed batch-two experiments preserved exact GPU outputs but increased observed p95 under contention, so the production path remains serialized. The engine logs GPU-lock wait, encoder, RNNT and finish-stage timings to distinguish queueing from CPU preemption. No Bonsai/Fish models were stopped for these runs.

Adaptive-race receipts (two simultaneous real paced Opus dictations through the supervisor, immediate ✓): ten idle-GPU finishes gave **p50 0.015 / p95 82.72 ms** server flush (`gpu-probe/pairs-10-adaptive-idle.jsonl`). Six finishes alongside an admitted, bounded 2048×2048 FP16 matmul co-tenant (GPU busy ≥75%) gave **p50 219.18 / p95 235.99 ms**, with CPU winning five of six races; queued GPU encodes took ~100–220 ms and CPU completion of the final buffered 120 ms plus 100 ms silence took ~197–216 ms, followed by ~11–25 ms cleaner (`gpu-probe/pairs-6-adaptive-gpu-cotenant.jsonl`; `probe_gpu_cotenancy.py`). Six finishes beside three bounded single-thread CPU workers gave **p50 75.49 / p95 115.95 ms** (`gpu-probe/pairs-6-adaptive-cpu-cotenant.jsonl`; `probe_cpu_cotenancy.py`). Eight CPU-only fallback finishes while a Fish job blocked GPU admission gave p95 **326.05 ms** (`gpu-probe/pairs-8-cpu-fallback.jsonl`). These small samples characterize the conditions, not a universal latency bound. Fulfilling ≤100 ms even under heavy co-tenancy requires either isolating sufficient CPU capacity, preemptible GPU capacity, or changing the last-step compute substantially; the hedge preserves availability and often wins over a busy GPU, but does not establish the requested bound.

The original FP16 ONNX graph has 6,206 nodes. ORT MIGraphX rejects it at `simplify_reshapes: add: Dimensions do not match` even after static-shape conversion; ONNX2Torch eagerly runs its thousands of Python operators at ~180 ms/step. Native Transformers modules are the maintained GPU route instead. The CPU route remains the safer path when GPU admission fails and is still the only Converge route.
