# Memory and accountable custody

Working memory is one granted Markdown folder per owner. `PI_KENAN_MEMORY_FOLDER` is an explicit absolute path supplied by the authenticated scope; there is no guessed home or administrator folder. [markdown.ts](src/markdown.ts) requires nonempty canonical `README.md` and `AGENTS.md` pointer files. Each turn reads the current `authority.md` head again, checks revocation/validity, and injects only active authority alongside the pointers. Historical versions never supply current authority. Unset/unavailable/fenced folders supply no expanded standing authority. Read only notes relevant to the task and update the owning note before finishing active work.

The folder owns facts, decisions, work, calendar data, stated delegation and steering. Its README links `authority.md`, `work.md`, `calendar.md`, `steering.md` and source records. Authority remains stated, scoped and subject to validity, revocations, spending limits, exclusions and third-party consent; predictions are not grants. Calendar is structured memory data linked by dataset ID from `calendar.md`, retaining exact times/timezones, recurrence, ICS sources, settings and deletion undo. The agent's `memory_data` tool uses the granted dataset; there is no calendar UI, feed endpoint or controller.

## Facts, authority and source reconciliation

Notes retain stated/revealed/derived/hypothesis provenance, evidence and counterevidence, actual observation and validity times, corrections and retractions. Unknown confidence, deadline, recommendation or freshness stays unset. Following an agent suggestion is agent-exposed evidence, not independent confirmation of a preference. Removed/stopped evidence cannot remain a current authority claim.

Record source coverage only after actual work: which permitted source was inspected, when checked, when reconciliation completed, its freshness boundary and complete/partial/inaccessible/excluded state. Reading a note, refreshing a surface, scheduling a check or ending a turn does not reconcile its sources. A later source check can retain an earlier reconciliation date without claiming a new completion; unknown freshness never means perpetual freshness. First apply the owner's exclusions and third-party consent, before capture or inference.

## Unified grants

[permissions.ts](../orchestrator/src/permissions.ts) is the core principal/resource/action contract for operations, models, tools, threads, memory and data. Configuration supplies explicit grants and consent, with provenance and validity. Ownership, a name, Unix UID, room membership or operational privilege is not an implied allow. Deny wins. Rooms require the complete verified audience to have read/disclosure grants, and protected subjects must consent to the actual recipients/action. Trusted core configuration and authenticated scope/resource registries supply identities; request bodies cannot self-issue grants.

`memoryService(options)` is exported as `kenan-memory/service`, with `MemoryServiceOptions`, `MemoryAuth`, `MemoryPrincipal` and `MemoryAuthorizer`. It returns an embeddable Node HTTP server; core may attach its request listener. Required options: `store`, `auth`, `enabled`, `authorize`. The `authorize({caller,route,input})` callback runs after credential/session authentication and before every operation, including session issuance and private consultation routes. It returns the unified `PermissionResult<Authorization>` synchronously. The same decision is repeated with `record: {about, obviouslyPrivate?}` for each actual record before read/disclosure reports or mutation. Private consultation roles do not bypass record scopes; absent and inaccessible delete targets receive the same denial. Unset authorization returns 503; denial returns 403 without mutation. The callback maps authenticated callers and trusted resource descriptors through core's actual policy, not caller-selected grants.

Memory HTTP and consultation admission keep their authenticated setting, provenance, privacy, complete audience and log-before-disclose guards. These are additional restrictions, not an alternative grant source. The shared core owns principal authentication and authorization adapters. Raw database handles are custody-only, not public authorization APIs. Standalone custody startup requires `PI_KENAN_MEMORY_AUTHORIZATION_MODULE` exporting `memoryAuthorizer({auth,store})`; shared core embedding is the service owner.

[core/memory.ts](../orchestrator/src/core/memory.ts) adopts the existing database and credential file under a declared confidential custody scope. Its config names `id`, `uid`, `custodyScopeId`, exact database/auth/receipt paths, authenticated identity selectors, resource descriptors and endpoint/operation/action mappings. Registered resource handles prove the same device/inode in the pinned namespace; the old-owner detached receipt and exclusive database lock are required before opening. A missing database/schema never becomes a new ledger. The explicit `datasets` array adopts additional owned data through that gateway; `[]` means none. `createCoreMemory` returns a promise so failed multi-store adoption releases acquired custody before returning its error. Closing drains accepted handler promises and data commands, then releases stores, locks and namespace resources. No separate memory engine/listener is needed. `markdownOwners` explicitly maps each subject to its folder, resource and custody scope. `projectionMaintenancePrincipalId` is a registered service ID (or explicit null when no folders); that service needs each folder's read/invalidate grants. It never impersonates the folder owner. Locked/unadopted personal folders and datasets remain unavailable descriptors without folder access; configuration reload after unlock activates them. The owning scope's registered `PI_STACK_HOST_CONFIG` file conserves the live `oneKenanEnabled` stop; missing/invalid flags do not enable shared custody.

## Structured memory data

[calendar-data.ts](src/calendar-data.ts) is the first structured adapter, mounted by [core/calendar.ts](../orchestrator/src/core/calendar.ts). Config declares `id`, `person`, `custodyScopeId`, existing `databasePath`/`adoptionReceiptPath`, `memoryFolder`, `journalDirectory` and a private data `resource`. Every path must be registered in the exact adopted scope's namespace. The old database must already contain events, subscriptions, settings and delete undo; startup neither creates replacement stores nor migrates/deletes settings.

`POST /v1/memory` with `operation: data`, explicit `dataset`, `requestId`, `command` and authenticated read `context` is the only data transport. Its mapped execute grant is followed by exact dataset read/write/delete authorization for the command. Neither owner identity nor private consultation role grants access. The ordinary/root tool derives stable request IDs from thread/tool-call identity; committed command receipts make restart/retry idempotent and reject changed payloads.

Calendar commands: `snapshot {from,to}`, `records`, `export-ics`, `receipt {requestId}`, `create {event}`, `update {id,target,patch}`, `delete {id,target}`, `restore {undoToken}`, `subscribe {name,url,zone}`, `unsubscribe {id}`, `refresh {from,to}`. Targets are explicit `{kind:series}` or `{kind:occurrence,start}`. Creation requires title/start/end/zone/allDay/location/notes/repeat/repeatUntil; unset repeat is not invented. Empty location/notes and null repeat/repeatUntil are explicit valid values. Snapshot/refresh ranges use offset-bearing instants, ordered and at most two years. Imported events remain read-only; undo uses exact post-delete comparison before restoring.

Subscriptions save sources without fetching. A manager-owned duty may invoke finite `refresh` on previously saved sources under the dataset's write grant/consent; there is no timer or per-agent calendar lifecycle. Refresh is bounded to 20 seconds and 4 MiB per source, retaining the last successful ICS and explicit failure state. Mutations keep committed data receipts and use the existing action outbox under the configured journal custody. Inspect a receipt before repeating an unavailable mutation. `records` includes private settings/ICS custody, so it cannot be mounted as public data.

## Adopt existing data without discarding it

[Executable cutover plan](../../docs/memory-adoption.md) gives the per-subject template, final writer-transfer boundary and metadata-only receipt contract.

[adoption.ts](src/adoption.ts) exports a read-only source snapshot into the granted folder. [memory-adopt.ts](../../scripts/memory-adopt.ts) accepts only `--plan /absolute/root-owned/plan.json`; the plan must be canonical and not group/world writable. It declares the actual principal, PermissionPolicy, source data Resource/path/format/selection and destination memory Resource/path. The function checks source-read and destination-write grants and consent before opening the source. Destinations cannot weaken confidentiality or move a whole store to another owner.

```sh
bun scripts/memory-adopt.ts --help
bun scripts/memory-adopt.ts --plan /etc/pi-stack/memory-adoption.json
```

The plan is a host-owned migration declaration, not a new grant issuance interface. No private export is run as part of source implementation.

- `format: memory` decrypts **every selected life version**, including policies, steering, entity corrections/retractions, source coverage and import receipts; head status and exact provenance are retained. Subject keys stay in custody and never enter Markdown. Memories retain stopped state. Disclosure and consent journal records retain exact bodies and IDs.
- `selection: {kind: person, person: ID}` exports that person's life records and only exclusively tagged memory/disclosure records. Mixed/shared material remains in the original restricted journal. `selection: {kind: whole-store}` is for the original custody owner's restricted folder under an explicit whole-source grant, never a person export shortcut.
- `selection: {kind: custody-subject, subject: ID, custodian: OWNER}` keeps a service policy subject distinct from its actual source/destination owner. A service principal needs explicit read/write grants/consent, source subject inclusion and a singleton destination subject. This memory-only projection selects all that subject's life versions/current head without copying native memory/disclosure/private consultation journals. Its folder scope owner is the custodian, not an invented person matching the subject.
- `format: calendar` copies events, subscription bodies/ICS, settings and deletion-undo custody from the declared person's calendar source. This preserves timezone and exact source fields; it does not create events or fetch feeds.
- A person export installs exactly the selected current policy head in `authority.md`. Historical policy versions remain provenance records. The result's `currentHead` is metadata only: `{source,subject,revision,sha256}`, or null. Whole-store exports create provenance records, not an aggregate biography/work/authority note.
- Content-addressed `.md` records contain exact original values. The source fingerprint manifest links them. Atomic exclusive writes reuse identical records, reject changed content, preserve hand-edited owning notes and pointer files, and publish the receipt last. A failed run leaves source untouched; rerun continues the same snapshot without duplicates.

The result's `ownershipPaths` identifies created/replaced paths and exact matching generated files/directories. The owning custody helper must hand these to its explicit registered target UID/GID before activation; the CLI neither infers identity nor chowns. This list remains available on idempotent retry, including CAS-replaced authority files; unrelated hand-edited notes are excluded.

For cutover, first drain and detach the original writer, then run adoption against that final source. If an earlier snapshot was adopted and the authority head advanced, put its returned `currentHead` into the final plan's `expectedAuthority`. The command replaces only the exact prior rendered head with matching source/subject/revision/digest and a newer source revision; conflicting hand edits and unrelated authority fail. Re-running the final plan retains every selected historical version and returns the final fingerprint/head receipt. A snapshot receipt taken while the source could still mutate is not cutover approval.

Adoption never deletes source databases, changes grants, resets effects, reopens stopped work, renews authority or replays uncertain actions. Credential/session material and external-action fences remain with their native owners. Host activation must bind existing sources and accepted custody before retiring any owner.

## Independent action, disclosure and consent custody

[contract.ts](src/contract.ts), [store.ts](src/store.ts) and the authenticated memory service retain the accountability journal. This is not a live life/task ledger. Person tools query their own exclusively tagged facts and nonprivate recipient-relevant actions; broader shared/private facts go through a granted private consultation. Stopped records do not return from searches. Private consultation captures are not ordinary own memory merely because an old row attributed them to the requester; interpretation changes at read/search/forget boundaries without rewriting historical provenance. Independently public recipient-relevant action receipts keep their intended access. New captures record their actual authenticated service custodian.

Delete/stop-using requires the person's actual choice. After existing credential, ownership and record grants, forget stages signed `FORGET-PENDING.md` fences before the native source commit, scrubs active copies/index links, and invalidates transitive derived/hypothesis evidence across explicitly registered folders. Inferred authority is removed; independently stated grants remain. Per-folder fences contain only that folder's own known metadata/text, not another owner's private content. Native `forgotten_sources` correction IDs prevent re-adoption and support deferred locked-folder invalidation. Failed/missing housekeeping grants leave the source unchanged or pending and active reads/current-head injection unavailable, never false successful forgetting. Restart verifies signed fences and resumes idempotently under the same explicit maintenance grants; disclosure/action records remain independent. Action replay deduplicates by verified person and external ID; forgotten actions retain replay tombstones.

[Person guidance](person.md) keeps each thread transparent. [Private discretion](discretion.md) and [root operations](../kenan-root/README.md) preserve full verified audience, fresh private consultation, exact chosen replies, log-before-disclose, consent questions/answers and restart-safe delivery. Only selected replies cross into ordinary or room conversations, never private context or traces.

[External-action authority](../../docs/action-journal.md) remains the effect owner: canonical business intents, recipient holds, provider evidence and uncertainty reconciliation. The [journal](src/journal.ts) projects supported outgoing actions. Unjournaled sends require an actual-action memory receipt with only recipient-relevant content. Markdown never stands in for a provider receipt or release of an unresolved recipient fence.

## Operation

Source is built with `npm run build --workspace=kenan-memory`; focused fixtures use `bun test packages/kenan-memory/tests/adoption.test.ts` and `packages/orchestrator/tests/permissions.test.ts`. Fixtures use disposable databases only. Installed journal custody remains encrypted under its owning mount, with real gocryptfs admission and no plaintext-directory substitution. Host activation owns folder paths, explicit grants, exact source identities and core wiring; source code does not grant private-folder access or run an export.
