# Kenan memory

One encrypted host memory and disclosure account, gated by `host.oneKenan === true`. The [contract](src/contract.ts) is shared by person tools, root execution, the action journal and rooms. [Person guidance](person.md) keeps user threads fully transparent; [root discretion](discretion.md) governs the privileged context. Root's reply is the only outward channel; its private context never enters a user thread.

## Custody and identity

`pi-kenan-memory.service` runs as `pi-kenan` beside existing units and joins `pi-kenan-custody.service`'s mount namespace. Production SQLite is `/var/lib/pi-kenan/private/memory/memory.sqlite3`. Startup waits for the actual gocryptfs mount, never opening a plaintext directory underneath it. Custody owns encryption keys and mounting. Systemd loads root-owned `/etc/pi-stack/kenan-memory-auth.json` as a credential. Person Unix identities and existing supervisors are unchanged.

Authorization configuration:

```json
{
  "supervisors": [{ "person": "alice", "displayName": "Alice", "token": "a random supervisor credential" }],
  "uidPersons": { "1001": "alice" },
  "publisherToken": "an optional distinct action-publisher credential",
  "rootToken": "a distinct root-service credential"
}
```

Real credentials are generated by custody and never committed. Still-distinct Unix supervisors may authenticate by the Linux loopback connection's UID. A fixed per-person supervisor credential also works (`PI_KENAN_MEMORY_SUPERVISOR_TOKEN_FILE` or `CREDENTIALS_DIRECTORY/kenan-memory-supervisor`). The server mapping identifies the person: names/roles in request bodies grant nothing.

`POST /v1/sessions` accepts only `{threadId}`. Supervisor credentials or mapped UIDs mint **person** sessions, never root sessions. The returned `{ok:true,value:{person,threadId,token,role:'person'}}` binds both person and thread and survives memory-service restarts. `openPiSession` clears inherited memory identity but does not connect to the memory service. The extension registers tools/guidance without a capability or network call. On an already-open ordinary thread, the inert extension activates on the next flag-on turn. Only execution of a memory or `ask_kenan` tool lazily mints a verified capability; a custody/service outage returns a typed tool error, never blocks ordinary session initialization or builtin-only turns. Root sessions still require their admitted root capability and never fall back to a person mint. Flag-off turns remove active memory/ask tools and add no guidance. Initially flag-off sessions have no new tools or network work. Parallel tool calls share one in-flight mint, and failed mints can retry on a later tool call without replaying any side effect. Raw, sandboxed and isolated application sessions never receive household memory.

## Person tools

User threads are fully transparent. Their direct view contains only facts recorded by their own person with no other subjects, plus **nonintimate action records** explicitly affecting them. Mixed/private facts, unrelated records, private actions, shared forgetting and broader accountability require `ask_kenan`. A missing item in the direct view does not prove it never happened.

Tools: `memory_search`, `memory_read`, `memory_write`, `memory_forget`, `memory_disclosures`, `memory_log_disclosure`, `ask_kenan`. Rooms register only `ask_kenan`; the room runtime separately supplies asynchronous questions and enforces that two-tool whitelist. Root registers unrestricted memory tools, not recursive `ask_kenan`.

`ask_kenan({request})` calls the separate root service with the verified session token and an opaque request UUID stable per thread/tool call. It promptly returns an accepted/pending receipt; root's chosen reply or safe terminal status then arrives automatically in the originating thread. Continue other work rather than polling. `ask_kenan({requestId})` alone retrieves the existing request via authenticated GET without a new root model session or repeating any side effect. Only the chosen reply or public request status returns; root session IDs, transcripts, tools, traces and credentials never return. `PI_KENAN_ROOT_URL` selects the configured endpoint, otherwise loopback `PI_KENAN_ROOT_PORT` or 18821. The person cannot select root's model, prompt, tools, context or audience. Root HTTP failures, transport failures, cancellation and the 20-second transport deadline are diagnosed separately without echoing any root response/error body. Cancellation or a lost acknowledgement returns the recoverable request UUID and never automatically replays the request. Already-cancelled calls do not submit anything. A failed/interrupted operation may already have acted and must not be resubmitted. Operational logs contain bounded stage/reason/status/duration fields, not private content or identities. `GET /v1/health` reports the memory process's startup-pinned `releaseCommit` without reading records.

## Memory API

`POST /v1/memory` accepts the `MemoryRequest` union and returns `MemoryResult`. All routes use `x-kenan-memory-session`. The client never throws network failures. Default memory listener is IPv4 loopback port 18820.

- `write`: text, subjects, source (`saidBy` or `actedFor`, optional action/external ID), verified setting, occurrence time and privacy. Recorded time/person are server-owned. Person writes require own provenance/subjects, except actions performed for that person may tag those affected.
- `search` / `read`: ranked OR retrieval with Porter stemming and diacritic-tolerant tokenization. Extra natural-language terms do not make all matches disappear. Empty queries list recent accessible items. About filters use registered person IDs. Returned items carry `readReport`; root cross-person consultations are logged automatically before data returns. This is a consultation record, not a claim that the person saw its contents.
- `forget`: `delete` removes the current item, securely deletes SQLite/FTS storage and checkpoints/truncates WAL; `stop-using` keeps custody but excludes it from every normal read/search. Tool calls without a mode post a clarification and change nothing. A person may only forget their own exclusively tagged stored records; shared forgetting goes through root.
- `log-disclosure`: additional actual disclosures through another channel. Root replies are accounted for by their delivery boundary, not by model tool use.
- `disclosures`: own-only entries for a person; root can consult the full account and select a subject. Person clients cannot retrieve mixed-subject disclosures or somebody else's account.

Action replay deduplicates by verified person plus `source.externalId`. Forgotten actions retain only an ID and hashed replay key, returning `{id,forgotten:true}` on retry rather than resurrecting text. Publisher credentials may write identified actions, never read/forget/disclose. Supported sends are journaled; unjournaled sends (browser webmail, raw SMTP, raw signal-cli) require a manual memory action record with recipient-relevant content. The [journal](src/journal.ts) owns dispatch custody and draining.

## Root boundary

Only the root-service credential can call these routes:

1. `POST /v1/root/admit {callerToken,request,rootSessionId?}` resolves a minted **person** session, obtains the current trusted room audience if applicable, records admission, and internally creates a **root** memory session. Returns `RootAdmission` to the root service only. Requests cannot supply identity/audience/model/prompt/context. Root roles never come from a person name or public mint.
2. Root executes in a fresh host-controlled session using that `memoryToken` and `PI_KENAN_MEMORY_ROLE=root`. Memory reads record conservative subjects; root execution also accounts for subjects touched by file/action work.
3. `POST /v1/root/finalize-reply {rootSessionId,reply,subjects,recipients?}` validates the admitted audience, rechecks live room membership, unions request/read/executor subjects and commits the exact reply atomically before acknowledgement. Refusals with no reads are logged too. Root's session token is then revoked. Repeated identical finalization is idempotent; changed replies or audiences are refused.

### Durable request status and notifications

Root-only `POST /v1/root/authorize-request {callerToken,rootSessionId}` validates the minted person's original identity/thread and the live full room roster. It returns only an authorization acknowledgement to root, never a new admission or memory capability. Renewed person capabilities for the same identity/thread can recover an existing request; another person/thread cannot.

Root-only `POST /v1/root/log-request-status {rootSessionId,requestId,status:'failed'|'interrupted'}` chooses and idempotently logs a fixed generic operational notice. The caller cannot provide notice text. Current room identity and full roster are checked before every delivery attempt, including after an earlier accounting acknowledgement.

Root-only `POST /v1/root/log-notification {rootSessionId,notificationId,recipient,text,subjects,obviouslyPrivate}` requires an admitted root session and registered individual recipient. Exact disclosure accounting and a recipient-relevant `notification-queued` action record commit atomically before delivery; this record does not claim the message was delivered. Identical retries acknowledge the same record; changed recipient/text/subjects/privacy under one notification ID are refused. The root service's encrypted outbox owns actual delivery and retries, not this memory store. [Root operations](../kenan-root/README.md) own both durable request replies and notifications.

### Durable consent continuation

The root-service credential also owns `/v1/root/log-consent` and `/v1/root/resume-consent`. No person or admitted root-session token may call either route.

- `log-consent {rootSessionId,consentId,subject,kind:'question'|'answer',text}` commits exact question/answer text before delivery or use. The subject must be a registered individual. A question is addressed only to that subject; the private answer is addressed to Kenan, not automatically to the original requester. Answers require a matching question record for the same subject. Repeated identical events are idempotent; altered subject/text is refused.
- `resume-consent {rootSessionId,subject,question,answer,consentId}` requires an authenticated original root admission and exact logged question/answer records. The original need not have produced a reply: a restart may interrupt it after the question was delivered and before it chose any outward text. It creates a fresh root admission preserving the original authenticated requester, originating thread and full audience, unioning the subject into accountability. Current room membership is rechecked; a changed room fails closed. Request bodies cannot set person, recipients, context or role.
- Resuming an unfinished origin atomically revokes its memory capability and marks it superseded; a late original executor cannot finalize an outdated reply. No initial reply is invented. Already-finalized original replies remain immutable and retry-idempotent.
- Resumption is durably idempotent per original root session and consent ID, including across memory-service restarts. Different data under that ID is refused. If the resumed root reply has already been finalized, its memory token is revoked as usual; the consent outbox must retain delivery/execution state and must not re-execute a completed reply. Root execution and the encrypted durable consent outbox are owned by the root service, not this store.

No list/history/context/trace/file/debug API is exposed here. Administrator root-session inspection is separate. The room resolver is host-owned `roomAudienceResolver` from Remote's `server/room-audience.mjs`; `pi-rooms` cannot downgrade an unknown room into a personal audience. The memory unit configures `/var/lib/pi-remote/one-kenan/rooms.sqlite3` and the immutable deployed callback module.

## Build and operation

```sh
npm run build --workspace=kenan-memory
bun test packages/kenan-memory/tests
# Integrator/publication only: additive source + unit install, no starts/enables
./deploy/kenan-memory
```

Runtime's immutable dependency closure includes compiled modules, source and both guidance files; Node and Bun exports resolve the same committed package. Service/CLI source is selected at `/srv/pi/kenan-memory`. Source/unit installation does not restart existing services. The integrator owns `deploy/host` wiring and the flag flip.

Fixtures run `bun packages/kenan-memory/src/main.ts` with `PI_STACK_HOST_CONFIG`, `PI_KENAN_MEMORY_AUTH_FILE`, reserved `PI_KENAN_MEMORY_PORT`, and a temporary `PI_KENAN_MEMORY_STORE`. An explicit fixture store omits production mount admission unless `PI_KENAN_PRIVATE_DIR` is supplied. Production units always set that mount. Rooms add `PI_KENAN_ROOM_AUDIENCE_MODULE` and `PI_REMOTE_ROOMS_DB`. Never point fixtures at live state.

Rollback clears the host flag and stops the new units; encrypted memory remains intact. Tests change no live service, mount, key or person registry.
