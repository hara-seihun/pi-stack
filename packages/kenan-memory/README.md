# Kenan memory

One host-owned memory and disclosure account, used by ordinary conversations when `host.oneKenan === true`. Missing/false means no service listener, memory tools or discretion instructions. Raw, sandboxed and isolated application sessions do not receive household memory. The [contract](src/contract.ts) is shared by tools, the action journal and trace privacy. [Discretion](discretion.md) is guidance to Kenan, not a coded content ACL.

## Custody and identity

`pi-kenan-memory.service` runs as the dedicated Kenan execution identity beside existing units. It joins `pi-kenan-custody.service`'s mount namespace. The production SQLite store is `/var/lib/pi-kenan/private/memory/memory.sqlite3`; startup waits for the actual gocryptfs mount, never opening a plaintext directory in its place. Custody owns the encryption key and mount. Systemd loads the root-owned `/etc/pi-stack/kenan-memory-auth.json` as a credential. No person receives the store or custody keys.

Authorization configuration:

```json
{
  "supervisors": [{ "person": "alice", "token": "a randomly generated supervisor credential" }],
  "publisherToken": "an optional distinct write-only action publisher credential",
  "uidPersons": { "1001": "optional distinct-UID local supervisor identity" }
}
```

Real credentials are generated by custody and never committed. A per-person supervisor receives `LoadCredential=kenan-memory-supervisor:...`; alternatively set `PI_KENAN_MEMORY_SUPERVISOR_TOKEN_FILE`. Its fixed server-side token mapping identifies the person. A name in JSON does not. For still-distinct Unix identities, the existing Linux loopback `/proc/net/tcp` UID pattern is supported. Shared-UID execution always needs credentials.

The supervisor calls `POST /v1/sessions` with `{threadId}` and `x-kenan-memory-session` containing its credential. The returned `{ok:true,value:{person,threadId,token}}` binds the session to the verified person/thread and survives service restarts. Ordinary `openPiSession` performs this mint, clears inherited memory identity and supplies `PI_KENAN_MEMORY_PERSON`, `PI_KENAN_MEMORY_TOKEN`, `PI_KENAN_MEMORY_URL` to tools. Room context comes from `PI_REMOTE_ROOM_ID`. Authenticated room speakers are recorded in source provenance; the connection owner remains the custodian.

## API and tools

`POST /v1/memory` accepts the `MemoryRequest` union, returns `MemoryResult`, and uses the same credential header. The client never throws network failures. `memoryClient` accepts an explicit token/URL; otherwise reads the session token or configured supervisor/publisher credential file. Default listener is IPv4 loopback port 18820.

- `write`: text, subjects, source (`saidBy` or `actedFor`, optional action/external ID), verified setting, occurrence time and privacy marker. Recorded time/person are server-owned.
- `search` / `read`: normal-use items only, with a per-turn `readReport` containing subjects and cross-person touch status. Pi tools persist it as `details.kenanMemoryRead`; trace privacy withholds affected turns. All room reads are marked, even empty ones.
- `forget`: `delete` removes the current item and truncates SQLite's WAL after secure deletion; `stop-using` keeps custody but excludes the item from every normal read/search. Tool `memory_forget` without a mode posts an asynchronous clarification and changes nothing.
- `log-disclosure`: exactly what Kenan told which audience about which subjects. The independent disclosure account is not erased by deleting a memory item.
- `disclosures`: entries about the verified asking person. A client cannot choose someone else as the accountability subject.

Tools: `memory_search`, `memory_read`, `memory_write`, `memory_forget`, `memory_disclosures`, `memory_log_disclosure`. Before returning another person's information, Kenan decides what belongs in the answer and logs the disclosure. Reads are not disclosures to the person at the client.

Action journal replay deduplicates by verified person and `source.externalId`. Deleted/stopped actions leave an ID plus a hashed replay key, not their content; retries return `{id,forgotten:true}` instead of resurrecting them. The journal publisher can write identified actions for a person but cannot read, forget or edit disclosure history. The [action journal](src/journal.ts) owns durable dispatch custody and draining.

## Build and operation

```sh
npm run build --workspace=kenan-memory
bun test packages/kenan-memory/tests
# Publication/integrator only: additive source + unit installation, no starts/enables
./deploy/kenan-memory
```

The runtime dependency closure includes the same committed source, compiled modules and discretion file for both Node and Bun consumers. The service/CLI release is selected at `/srv/pi/kenan-memory`. `deploy/host` integration and the flag flip belong to the integrator; this component does not modify or restart existing units.

For fixtures, run `bun packages/kenan-memory/src/main.ts` with:

- `PI_STACK_HOST_CONFIG`: fixture host JSON (`oneKenan: true`).
- `PI_KENAN_MEMORY_AUTH_FILE`: fixture credential mappings.
- `PI_KENAN_MEMORY_PORT`: reserved staging port.
- `PI_KENAN_MEMORY_STORE`: temporary SQLite file. An explicit fixture path omits production mount admission unless `PI_KENAN_PRIVATE_DIR` is also set.

Production units set `PI_KENAN_PRIVATE_DIR`; staging can supply its encrypted mount through the same variable. Never point fixtures at live state. Stop the new memory unit and clear the host flag for rollback; the encrypted memory remains intact. No service, mount, key or person registry is changed by the test suite.
