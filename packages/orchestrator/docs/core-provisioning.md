# Canonical account provisioning

Fresh account creation and existing account unlock are separate operations. The owning authenticated registration source prepares explicit principals, grants, scope resources and namespace custody. It records the creator in a root-owned registration; no request body, UID or display name grants authority.

`CoreProvisioner` in `src/core/provision.ts` accepts owner-authored registrations and an already authenticated principal ID. A record includes a stable registration ID and request ID, creator principal, provenance source, operation resource, complete `CoreScope`, exclusive fresh storage directory, and explicit manager workspace/model/thinking/speed. The creator needs an active `execute` grant on that operation; the registered person needs `read`, `dispatch` and `control` on the person-owned thread scope. The declared manager ID is fixed before any storage effect.

All four scope storage descriptors are distinct direct children of the exclusive directory. The owning host must register and validate its mounted parent and manager workspace. A locked/inactive scope is never read or initialized. An existing directory without the exact creation reservation is an ownership conflict, not an invitation to reconstruct it.

The helper reserves that directory, locks its creation ledger, checkpoints database/key identity, creates the thread schema and one idle dispatch-only Kenaznia, detaches the preparation connection, then writes the normal dev/inode-bound controller adoption receipt. It never opens a native/model session. Repeating the exact registration returns the existing receipt. A partial crash after manager commit resumes the original spawn receipt and key, not a replacement manager. Missing or changed accepted storage is an error; no state is wiped. SQLite and reservation records are private owned files.

The host entry is `provisionRegisteredAccount({configPath, registrationPath, requestId})` in `src/core/provision-command.ts`. It requires the owning effective-root operation and nonredirected root-owned documents, with no actor override. The registration document is `{version:1,registration:CoreProvisionRegistration}`. Its scope must exactly match the canonical config. The host validates the registered namespace and existing ancestor before creation. `deploy/core-host.mjs` owns the account binder/command adapter.

After preparation, the verified account owner updates the shared resource view and canonical configuration, then asks the existing core process to reload through its trusted SIGHUP entry. Completion requires health/adoption evidence for the target scope; signal acceptance alone is pending. Existing unlocked accounts follow that same resource/config/reload path using their exact prior database, session/key identities and detached custody receipt, without invoking fresh provisioning. The shared core remains the only running controller.
