# Canonical account provisioning

Fresh account creation and existing account unlock are separate operations. The owning authenticated registration source prepares explicit principals, grants, scope resources and namespace custody. It records the creator in a root-owned registration; no request body, UID or display name grants authority.

`CoreProvisioner` in `src/core/provision.ts` accepts owner-authored registrations and an already authenticated principal ID. A record includes a stable registration ID and request ID, creator principal, provenance source, operation resource, complete `CoreScope`, exclusive fresh storage directory, and explicit manager workspace/model/thinking/speed. The creator needs an active `execute` grant on that operation; the registered person needs `read`, `dispatch` and `control` on the person-owned thread scope. The declared manager ID is fixed before any storage effect. Fresh ordinary scopes declare `PI_SESSION_WRITER_DIRECTORY=/run/pi-stack/session-writers/UID`, `PI_SESSION_WRITER_SCOPE=scope.id`, `PI_NATIVE_RUNNER_DATA_DIR=scope.custody.dataDir` and `PI_NATIVE_RUNNER_UID=UID` as a string, plus exact directory resources `/run/pi-stack/session-writers/UID` and `/run/pi-stack/native-runner-locks/UID`. UID is the actual fresh executor, `scope.custody.uid`, never an inferred Root identity. The owning host runs `core-host.mjs prepare-writers ARTIFACT CONFIG` to prepare physical owner-only directories outside FUSE before provisioning; this prepares fences without unlocking storage.

All four scope storage descriptors are distinct direct children of the exclusive directory. The owning host must register and validate its mounted parent and manager workspace. A locked/inactive scope is never read or initialized. An existing directory without the exact creation reservation is an ownership conflict, not an invitation to reconstruct it.

The helper executes as the registered Unix owner, reserves that directory, locks its creation ledger, checkpoints database/key identity, creates the thread schema and one idle dispatch-only Kenaznia, detaches the preparation connection, then writes the normal dev/inode-bound controller adoption receipt. It never opens a native/model session. Registration `markdown` is explicitly `{kind:"none"}` or `{kind:"configured",folder,readme,agents}`: the UID worker writes absent nonempty `README.md`/`AGENTS.md` in that exact declared folder without overwriting existing text. Missing accepted Markdown is an error, not regeneration. Repeating the exact registration returns the existing receipt. A partial crash after manager commit resumes the original spawn receipt and key, not a replacement manager. Missing or changed accepted storage is an error; no state is wiped. SQLite and reservation records are private owned files.

The host entry is `provisionRegisteredAccount({configPath, registrationPath, requestId})` in `src/core/provision-command.ts`. It requires the owning effective-root operation and nonredirected root-owned documents, with no actor override. The registration document is `{version:1,registration:CoreProvisionRegistration}`. Its scope and any fresh image registry must exactly match the canonical config. The host supplies those exact four registered fields in the finite child's environment. The CLI worker rejects any mismatch before bootstrap; the preparation ThreadService receives the registered scope environment, never an ambient/default scope. The host launches finite `provision-worker.js` through `CustodyResources` in the registered namespace as its exact UID/GID; the worker validates the existing ancestor before creation. Only that registration and its relevant principal/grants cross stdin, not the full account config or credentials. A lost acknowledgement recovers the same reservation/request rather than replacing state. `deploy/core-host.mjs` owns the account binder/command adapter.

Registration `images` is required: `{kind:"none"}` or `{kind:"fresh",priorOwner:{kind:"none"},registry:CoreImagesSpec}`. A fresh registry belongs only to the new scope, has `relatedThreadScopeIds:[]`, distinct database/artifact/adoption paths as direct children of the reserved account directory, explicit canonical reference roots read as the owning UID, and a private/confidential own-person `dataResource`. `allowedRoots:["/"]` is valid when preserving the original own-UID filesystem ceiling; it does not register `/` as a thread workspace or allow root-identity reference reads. The original account-creation template must grant that person `read`, `execute` and `use` on the image resource. The host forwards these exact grants to the finite UID worker; it never infers image access from an account name or thread grant.

The same reservation checkpoints the image database/artifact inode identities before initializing the canonical seven-table schema. The image receipt binds the exact table names, original registration/request and explicit prior owner:none; it is detached preparation evidence for the ordinary `CoreImages` adoption owner, not a new engine. The receipt includes affirmative absent-source evidence for the idle fresh manager's native JSONL, so its first finalized image output remains recoverable even if emitted before the image owner starts. No image generation occurs during provisioning. Exact retries preserve existing image data and receipt bytes, including a crash between schema creation and detached receipt. Missing or changed accepted image state is an error. A configured new-account registry cannot be marked `none`; the pure OIDC producer also requires actual host images disabled before no-image enrollment.

`src/core/image-schema.ts` owns the portable schema used by both fresh provisioning and existing FK adoption. `tests/core-fresh-images.test.ts` runs the real finite subprocess UID worker and then starts the unchanged canonical image adoption consumer against its receipt.

After preparation, the verified account owner updates the shared resource view and canonical configuration, then asks the existing core process to reload through its trusted SIGHUP entry. Completion requires health/adoption evidence for the target scope; signal acceptance alone is pending. Existing unlocked accounts follow that same resource/config/reload path using their exact prior database, session/key identities and detached custody receipt, without invoking fresh provisioning. The shared core remains the only running controller.
